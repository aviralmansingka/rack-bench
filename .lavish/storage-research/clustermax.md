## 1. What ClusterMAX tests (storage)

ClusterMAX's hands-on testing runs in 3 phases — Audit (config, ~15 min), Performance (microbenchmarks + real-world), Reliability/Fault-tolerance — plus user interviews (200+ neocloud users) ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). Storage appears in all three.

### 1.1 What they request from providers (the storage under test)
- **10TB+ of high-performance file storage** supporting NFS/POSIX mounts **and** a ReadWriteMany (RWX) Kubernetes StorageClass via CSI driver; **10TB+ of S3-compliant object storage** ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). CoreWeave's own summary confirms the same ask: "high-performance file storage, S3-compatible object storage" ([CoreWeave blog](https://www.coreweave.com/blog/coreweave-becomes-the-only-provider-to-earn-three-consecutive-platinum-clustermax-tm-ratings)).
- Storage tiers are enumerated per provider: `/home`, `/data` (shared FS), `/scratch` (local NVMe), and any additional mounts ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 1.2 The actual storage performance suite (proprietary, hands-on)
All from the [3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard):
1. **fio (the core tool — yes, fio is used):** "We run fio, ior, Elbencho… The test that finds the most issues, though, is good old-fashioned fio. We sweep sequential/random reads/writes with buffered/direct I/O with 1MiB sequential blocks and 4 KiB buffered / 64 KiB direct random blocks from c1 all the way up to c32… We track throughput, IOPS, and latency, and of course we also discover inconsistencies in metadata if the test fails with too many clients." An internal run artifact (fio values JSON on the SemiAnalysisAI `ClusterMAX-internal` repo) is linked as evidence for their AWS FSx finding: [fio.values.json](https://github.com/SemiAnalysisAI/ClusterMAX-internal/blob/d039ae43c09bc20e32cfea67469f80069e90d2a8/runs/aws-eks-karpenter-b200/20260729-094037/tests/fio/fio.values.json#L34).
2. **ior** (parallel I/O benchmark) and **Elbencho** (multi-node benchmark incl. metadata ops) — same source.
3. **Custom Torch / Torch DCP checkpoint save/load benchmark** — same source.
4. **Custom "datagen" benchmark from Skild AI** — approximates a robotics data pipeline: aggregate write throughput generating MP4 video + parquet sensor datasets — same source.
5. **Object storage (S3):** the same suite run against an S3 bucket, plus a custom benchmark measuring **large-object sequential read/write throughput, small-object PUT/GET rates, and read latency (p50/p90/p99)** — same source.
6. **Filesystem endurance (reliability phase):** 7.5 min sequential mixed R/W + 7.5 min random mixed R/W **per client count** with fio, reporting bandwidth-over-time, IOPS, tail latency, degradation ("we have seen some providers have bandwidth degradation of almost 40% under load") — same source.
7. **Object storage endurance:** 15-minute mixed PUT/GET/LIST/DELETE workload measuring throughput degradation, p99 GET time-to-first-byte drift, throttling, errors (~10% spread observed) — same source.
8. **PVC lifecycle (Kubernetes):** repeatedly start a pod that mounts a volume, **writes and fsyncs a file**, then is deleted; teardown timed between cycles — same source.
9. **Per-storage-tier lifecycle tests:** fresh-cache `pip`/`uv` installs on each tier (home, shared FS, local NVMe scratch, other mounts), `import torch` timed from each location (LOSF detector: "on some filesystems with LOSF performance issues, it can somehow take 10-20 seconds"), and `vllm serve` time-to-`/v1/models` from shared storage (10-40s good vs >2min bad) — same source. The `import torch` LOSF test dates back to ClusterMAX 1.0 ([1.0 article](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus)).
10. **Incidental correctness probes:** cross-node POSIX lock enforcement — on Verda they found "100/100 exclusive-lock violations for both `flock()` and `fcntl()` across nodes" via virtiofs; concurrent HF downloads produced corrupted data and Elbencho `ENOENT` at 32 clients ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)); on Nebius `/mnt/data`, concurrent directory creation from 128+ ranks returned `EEXIST` from inconsistent metadata visibility — same source.

### 1.3 The audit phase (public `cmax` CLI) — what it actually checks for storage
- The audit "covers hardware inventory, software and firmware versions, GPU access, containers, scheduler configuration, networking, **storage**, health monitoring, and security" with pass/warn/fail/skip output ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- The public CLI's **`storage` audit profile is only "binary storage installation and configuration checks"**, and the core audit "collects cluster, host, GPU, storage, network, health, and security data. **It does not run the planned performance or reliability tests**" ([cmax README](https://github.com/SemiAnalysisAI/clustermax)). Code inspection confirms exactly **one** storage-specific check ID, `storage.rwxStatus` (Kubernetes RWX StorageClass), in `cmax/criteria_links.py` and `cmax/audit_report.py` of the public repo ([github.com/SemiAnalysisAI/ClusterMAX](https://github.com/SemiAnalysisAI/clustermax)); the collector gathers NVMe drive counts/GB and mount tables (`findmnt`) as inventory only — **no smartctl, no nvme-cli, no mdadm, no fio anywhere in the public code** (source: repo grep, same URL).
- The audit does catch inventory-level storage misconfigurations, e.g. "seven local NVMe drives unmounted on each node" on STN ([STN review](https://www.clustermax.ai/cloudreview/stn)).
- The full audit "omits criteria that require commercial, contractual, performance, reliability, provider-side, or scale-out network evidence" ([cmax README](https://github.com/SemiAnalysisAI/clustermax)) — i.e., most Storage criteria (durability SLAs, backups, DR) are **not** machine-verified.

### 1.4 The published Storage criteria (16) — what "coverage" means on paper
From [clustermax.ai/criteria/storage](https://www.clustermax.ai/criteria/storage): parallel FS out-of-the-box (Weka/DDN/VAST); managed S3-compatible object storage; K8s PVC/StorageClass incl. RWX; mounts stay mounted (no flaking); read/write performance measured and within expectations; throughput/latency documented; storage scales in performance and capacity (provider demonstrates or lets customers validate); automated backups with retention; cross-region replication/DR; point-in-time recovery for managed DBs; CSI/filesystem snapshots; immutable/WORM storage (object lock); published durability SLAs (e.g. 11 nines); backup encryption with CMK/BYOK; centralized backup monitoring + **restore validation**; checkpoint storage durability (replication factor, cross-AZ). Storage is one of the 10 scored dimensions of every rating ([criteria overview](https://www.clustermax.ai/criteria); also [vCluster's ClusterMAX coverage page](https://www.vcluster.com/clustermax), [hedgehog.cloud analysis](https://hedgehog.cloud/blog/the-sell-math-how-clustermax-2.0-ratings-translate-into-revenue)).

**Key distinction:** criteria 1-6 above are backed by the hands-on fio/ior/Elbencho/S3 suite (§1.2); criteria 7-16 (durability, backup, DR, snapshots, WORM, SLAs, restore validation) have **no described hands-on test anywhere in the 3.0 methodology** — they are documentation/provider-claim checks, consistent with the CLI's stated omission of "commercial, contractual… provider-side" evidence ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard), [cmax README](https://github.com/SemiAnalysisAI/clustermax)).

## 2. What it skips (with evidence URLs)

1. **No SMART / NVMe health / drive telemetry testing.** Neither the 3.0 methodology ([article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)), the criteria ([storage criteria](https://www.clustermax.ai/criteria/storage)), nor the public CLI code ([repo](https://github.com/SemiAnalysisAI/clustermax)) mentions `smartctl`, `nvme` CLI, media-error/thermal/wear-leveling checks, or any drive-health telemetry. NVMe appears only as (a) a scratch-tier mount target, (b) inventory counts of drives/GB, and (c) anecdotes of inaccessible or unmounted NVMe ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard); [STN review](https://www.clustermax.ai/cloudreview/stn)). Their silent-data-corruption detection (TinyMeg2-class checks) targets **GPU tensor cores**, not storage paths ([1.0 article](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus)).
2. **No mdadm / RAID / array-state or degraded-mode testing.** Zero mentions of RAID, mdadm, erasure-coding configuration, rebuild behavior, or degraded-array performance in any ClusterMAX release ([3.0](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard), [2.0](https://newsletter.semianalysis.com/p/clustermax-20-the-industry-standard), [1.0](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus), [criteria](https://www.clustermax.ai/criteria/storage), [repo](https://github.com/SemiAnalysisAI/clustermax)).
3. **No storage failure injection.** Their fault-tolerance phase injects GPU/network failures only (DCGM XID injection, synthetic kernel-log XIDs, PCIe bridge reset producing real XID 79, node reboots, K8s churn) ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). There is no killed storage node, no controller failover, no disk-loss simulation, no read-only-remount or unmount-storm test. Storage failures only appear when found incidentally (e.g. Together's storage NIC `operstate=down` race; Vessl's 863 GiB overlay filling the root volume to `DiskPressure`; Crusoe's kernel writeback softlockup freezing the NFS client's NUMA node) — all from the [3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard).
4. **No backup/restore, snapshot, or DR round-trip validation.** The criteria *ask* for automated backups, cross-region replication, PITR, CSI snapshots, WORM/object lock, and "restore validation" ([storage criteria](https://www.clustermax.ai/criteria/storage)), but the 3.0 hands-on suite contains no test that takes a snapshot, breaks something, and restores; no CRR failover; no object-lock/WORM verification. ClusterMAX itself notes providers lacking these (GMO "lacked snapshots, automated backups, and disaster recovery options") as an observation, not a test result ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). The cmax CLI explicitly omits criteria needing "commercial, contractual… provider-side" evidence ([README](https://github.com/SemiAnalysisAI/clustermax)).
5. **No data-integrity / bit-rot verification at scale.** No checksummed write-then-read-back of TB-scale datasets; the corruption they surfaced (Verda HF downloads, Elbencho `ENOENT`) was incidental, not a systematic integrity sweep ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
6. **No capacity/quota/thin-provisioning testing.** No volume-fill test, no quota enforcement, no overcommit behavior; the Vessl `DiskPressure` incident was accidental ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). The only capacity caveat they document is that fio results "significantly depend on how big the volume we've been given is" — i.e., they don't control for it (same source).
7. **No GPUDirect Storage (GDS) benchmark.** GDS appears only as a UX wish for CoreWeave ("enabling local GPUDirect Storage could be a 1 click button"), never as a measured path ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
8. **Short-horizon endurance only.** Storage endurance is 7.5+7.5 min per client count (fio) and 15 min (S3) — no multi-hour/day soaks, no full-volume write sweeps, no scrub/fsck validation ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
9. **No sustained bulk egress / data-migration testing (the internet/egress claim, verified).** The claim "ClusterMAX doesn't test internet/egress" is **outdated as stated but right in substance**:
   - **What they DO test:** 2.0 already timed WAN-*ingress* proxies — 22.1GB NGC PyTorch container pulls ("critical test of a provider's peering and local caching strategy") and a 15B phi-4 Hugging Face download ("a real-world test of sustained WAN throughput", median ~3.4 Gbps) ([2.0 article](https://newsletter.semianalysis.com/p/clustermax-20-the-industry-standard)). 3.0 added explicit "internet speed using multiple approaches for download/upload speed, mostly from Cloudflare" in the Lifecycle phase ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
   - **What they still DON'T test:** bulk **egress** — no test moves 10TB+ of data *off* the cluster to an arbitrary destination, measures sustained upload at scale, or validates egress bandwidth caps/throttling or egress billing. Egress fees are assessed only as a documented offboarding/lock-in criterion ("Hyperscalers famously have high egress fees… Most Neocloud Giants… do not charge egress fees") ([1.0 article](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus); 2.0 notes the fee trend only as market commentary ([2.0 article](https://newsletter.semianalysis.com/p/clustermax-20-the-industry-standard))). WAN observations in 3.0 (Crusoe 0.47-0.78 Gbps; Bitdeer ~0.1 GB/s; Firmus 0.25 Gb/s to NGC) are incidental anecdotes, not a suite ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). The commercial weight of egress is visible in CoreWeave marketing "Zero Egress Migration" around the same period ([CoreWeave announcement](https://finance.yahoo.com/news/coreweave-announces-zero-egress-migration-140500798.html)) — a dimension ClusterMAX does not quantify.
10. **No storage-security hands-on checks** (encryption-at-rest on storage tiers, CMK/BYOK operation, key rotation) — criteria exist on paper ([storage criteria](https://www.clustermax.ai/criteria/storage)) but no test is described in the 3.0 methodology ([article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
11. **Metadata ops only incidentally covered.** Elbencho is run, and EEXIST/lock violations were discovered ad hoc, but there is no mdtest-style millions-of-files create/stat/delete sweep, and LOSF is proxied by `import torch` rather than measured directly ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
12. **The public tool gives buyers zero storage performance coverage.** `pip install clustermax` gets you an audit that "does not run the planned performance or reliability tests"; its storage profile is binary-install/config checks plus one RWX criterion ([cmax README](https://github.com/SemiAnalysisAI/clustermax); code grep confirms only `storage.rwxStatus`, same URL).

## 3. User complaints (Reddit r/MachineLearning, X, HN)

Direct public complaints specifically about **ClusterMAX's storage-coverage gaps** are scarce — the loudest "storage complaints" in the ecosystem are about *providers*, and ClusterMAX itself is the main aggregator of those:

1. **No dedicated Reddit/HN thread found attacking ClusterMAX's storage coverage.** Searches of r/MachineLearning and Hacker News surface general GPU-cloud advice threads and only tangential ClusterMAX mentions (e.g. HN comment: "This is why it's not recommended to use providers below the Silver level in SemiAnalysis' rating index" — [news.ycombinator.com/item?id=49621546](https://news.ycombinator.com/item?id=49621546)). No thread alleging "ClusterMAX missed my storage failure" was found.
2. **ClusterMAX's own user research is the de-facto complaint log for storage.** From 200+ user interviews they report the "main two sources of user frustration with storage are when file volumes randomly unmount and when users encounter the Lots of Small File (LOSF) problem," with LOSF bad enough that "the time even to import PyTorch into the Python process will lead to a complete lag out" ([1.0 article](https://newsletter.semianalysis.com/p/the-gpu-cloud-clustermax-rating-system-how-to-rent-gpus)). IREN (resold by multiple providers) users report "multi-day power outages… **storage failures**, air quality controls leading to link flaps" ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
3. **Provider-level storage complaints ClusterMAX documented but did not systematically test for:** Verda's unenforced cross-node file locks and corrupted multi-client downloads; Nebius's `EEXIST` metadata races; Azure's `EAGAIN` at >4 fio clients on Azure Files Premium and unattachable `managed-csi-premium-v2` StorageClass; AWS FSx 9.2s p99 buffered-read latency; Together's NFS rejecting filenames containing ":" and "slow and unreliable" S3; Moonlite's inaccessible NVMe; Runpod's cluster with "no shared filesystem to test"; Vessl's ephemeral OverlayFS losing `/etc/passwd` mid-test — all from the [3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). Each was found ad hoc, underscoring that no systematic lock/metadata/integrity suite exists.
4. **HN criticism targets ClusterMAX's claim-based criteria generally** (relevant because Storage criteria 7-16 are claim-based too): an HN commenter complains SemiAnalysis "made this [SOC 2] a base requirement… and then getting hacked themselves… it is just a pay-to-play checkbox" ([news.ycombinator.com/item?id=46137514](https://news.ycombinator.com/item?id=46137514)). A third-party review similarly cautions that "ClusterMAX does not publicly disclose every security test or every provider result. Buyers should not treat its tier system as a substitute for their own threat model" ([remio.ai review](https://www.remio.ai/post/clustermax-3-0-ratings-return-and-cheap-gpu-clouds-face-a-harder-test)).
5. **Users of the public CLI get no storage signal at all** — the tool's own README states it runs no performance/reliability tests ([cmax README](https://github.com/SemiAnalysisAI/clustermax)), so any community member auditing a candidate cluster with `cmax` today receives only binary/config storage findings.
6. **On the podcasts**, storage discussion is anecdote-driven (e.g. the Crusoe kernel-writeback softlockup that froze the NFS client's NUMA node for hours, discussed at ~37:01 in Ep. 033, [youtube.com/watch?v=gO7oczGh9qE](https://www.youtube.com/watch?v=gO7oczGh9qE); Latent Space Lightning pod [youtube.com/watch?v=MWX36ZYnsm0](https://www.youtube.com/watch?v=MWX36ZYnsm0)) — no listener pushback on storage coverage surfaced in transcripts.

## 4. Implications for a competing certification suite

A storage-focused acceptance/certification suite can outflank ClusterMAX on axes where its criteria are paper-only or its tests are shallow. Specific openings, each mapped to the evidence above:

1. **Drive health as a first-class gate.** SMART (HDD) + NVMe health (nvme-cli: media errors, critical warnings, percentage-used, thermal throttling) across every node, plus kernel-log I/O error scans — none of this exists in ClusterMAX today ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard); [repo](https://github.com/SemiAnalysisAI/clustermax)). This is cheap to run, objective, and buyer-legible.
2. **Storage failure injection and failover SLAs.** Kill a storage node / pull a member / flip an array degraded; measure client hang time, remount behavior, and recovery (their injection suite is GPU/network-only — [3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). This mirrors what buyers actually lose sleep over: Together's storage-NIC race and Vessl's DiskPressure went undetected by provider health checks until they broke tests (same source).
3. **End-to-end data integrity.** Checksummed write→read-back at 1-10TB scale, cross-node POSIX lock enforcement (productize the Verda 100/100 lock-violation probe), metadata consistency sweeps (productize the Nebius `EEXIST` probe) ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)). ClusterMAX measures performance, not correctness; correctness failures are exactly what cost a lab its checkpoints.
4. **Backup/DR round-trip certification.** Actually snapshot→corrupt→restore; verify object-lock/WORM; time a CRR failover. ClusterMAX lists these as criteria ([storage criteria](https://www.clustermax.ai/criteria/storage)) but runs no hands-on test and its CLI omits provider-side evidence ([README](https://github.com/SemiAnalysisAI/clustermax)). "Restore validation" is literally an unclaimed criterion.
5. **Bulk egress certification.** Sustained 10TB+ egress to an arbitrary S3/R2 endpoint, measured Gbps and cost — the missing complement to ClusterMAX's ingress-side tests ([2.0](https://newsletter.semianalysis.com/p/clustermax-20-the-industry-standard), [3.0](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)); commercially salient given CoreWeave's zero-egress positioning ([announcement](https://finance.yahoo.com/news/coreweave-announces-zero-egress-migration-140500798.html)).
6. **Capacity/quota/DiskPressure behavior.** Volume-fill to 90%+, thin-provision overcommit, ephemeral-overlay hygiene, `fsync` durability under node recycle — none tested today ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
7. **GDS (GPUDirect Storage) datapath benchmark** — direct-to-GPU reads/writes; unmeasured by ClusterMAX ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
8. **Long-soak endurance.** 24h+ mixed workload with degradation tracking; ClusterMAX stops at 15-30 min per client count ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
9. **Open, reproducible storage suite.** ClusterMAX's fio/ior/Elbencho/S3 suite is proprietary ("The rest we keep internally for now" — [3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)); its public CLI runs zero storage performance tests ([README](https://github.com/SemiAnalysisAI/clustermax)). An open-source storage acceptance harness would be the only tool buyers can run themselves.
10. **Positioning.** ClusterMAX's own contract-SLA appendix recommends "acceptance testing… across GPU compute, networking, storage and software" with a SemiAnalysis technical assessment as the vehicle ([3.0 article](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)) — meaning acceptance-day storage depth is currently sold as a consulting engagement, not a product. A standardized, automated storage acceptance certification plugs directly into that contractual moment.

## 10-line summary: the storage-coverage gap we can exploit

1. ClusterMAX 3.0's real storage testing is a performance suite: fio (c1-c32, seq/rand, buffered/direct), ior, Elbencho, a Torch/DCP checkpoint benchmark, a Skild AI datagen benchmark, and an S3 suite with p50/p90/p99 latencies.
2. Everything else in its 16 Storage criteria — backups, DR, snapshots, PITR, WORM, 11-nines durability, restore validation — is documentation/claim-checking with no hands-on test behind it.
3. Drive health is a blind spot: zero SMART, zero NVMe health/telemetry, zero nvme-cli/smartctl anywhere in methodology, criteria, or public code.
4. No RAID/mdadm/erasure-code state checks, no degraded-mode or rebuild testing, no storage-node failure injection — their fault injection is GPUs and network only.
5. No data-integrity verification: no TB-scale checksummed read-back, no bit-rot/silent-corruption sweep on storage (SDC checks target GPUs, not disks).
6. Correctness bugs (un-enforced cross-node file locks, EEXIST metadata races) were found by accident, not by a systematic correctness suite — a productizable gap.
7. Endurance is 15-30 minutes per client count; no long soaks, no capacity-fill/quota/DiskPressure tests, no GPUDirect Storage benchmark.
8. The "no internet/egress testing" claim is half-right: ingress/WAN downloads are tested (NGC container pulls, HF model pulls, Cloudflare speed), but bulk egress at 10TB+ scale, egress caps, and egress economics are untested.
9. The public `cmax` CLI runs no storage performance or reliability tests at all — its storage profile is binary-install checks plus a single RWX criterion — so buyers can't self-verify anything about storage.
10. Opening: an open, reproducible storage acceptance suite (SMART/NVMe health + failure injection + integrity/lock/metadata correctness + backup/restore round-trip + bulk egress + long-soak) would cover every axis ClusterMAX lists but doesn't test — at the exact contractual acceptance-testing moment ClusterMAX itself says should exist.
