# Hyperscalers — Published Network-Performance Methodology & Internet-Quality Diagnostics (AWS / Microsoft Azure / Google Cloud)

**Scope (verified):** This brief shows how the three hyperscalers *publish* network-performance methodology and *diagnose* internet quality. The scope covers bandwidth/burst documentation and benchmark runbooks (iperf3, NTTTCP, perfdiag). It also covers MTU/PMTUD guidance, path-diagnosis tooling (mtr/traceroute/Network Watcher/Network Intelligence Center), and monitoring metrics (CloudWatch, ENA `ethtool -S`). This brief is one of seven. All seven feed rack-bench's `bench internet` category for a Chennai datacenter node. That category covers sustained egress/ingress to public object stores, latency/jitter/loss, path audit, DNS health, and TCP health.

The node uses a ~2-hour certification window. PASS means **measured, never vendor-claimed**. Tagging convention used below: **[observed]** = directly stated in a cited source. **[calculated]** = arithmetic a source or this brief derives. **[inference]** = reasoning not stated by any vendor.

Research date: 2026-10-11. All claims below carry a source URL.

## 1. AWS — how Amazon documents and diagnoses network performance

### 1.1 The bandwidth model: baseline, burst, single-flow caps, and internet-gateway derating

- **Baseline vs burst ("instances with 16 vCPUs or fewer")** [observed]: "Typically, instances with 16 vCPUs or fewer (size `4xlarge` and smaller) are documented as having 'up to' a specified bandwidth; for example, 'up to 10 Gbps'. These instances have a baseline bandwidth. To meet additional demand, they can use a network I/O credit mechanism to burst beyond their baseline bandwidth. Instances can use burst bandwidth for a limited time, typically from 5 to 60 minutes, depending on the instance size." Credits refill only while an instance uses less than baseline. "burst bandwidth is a shared resource" — the resource stays best-effort even with credits. Inbound and outbound keep **separate network I/O credit buckets** ([EC2 instance network bandwidth](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)). The same page's CLI example gives concrete baselines: `c5.xlarge` baseline 1.25 Gbps, `c5.2xlarge` 2.5, `c5.4xlarge` 5.0.

  The `c5.9xlarge`/`c5.12xlarge` sizes run flat 12 Gbps. The `c5.18xlarge`/`c5.24xlarge`/`c5.metal` sizes run flat 25 Gbps [observed]. Each network spec table publishes per-instance baseline/burst numbers ([network specifications – general purpose](https://docs.aws.amazon.com/ec2/latest/instancetypes/gp.html)). The instance can *re-weight* bandwidth between VPC and EBS traffic ([EC2 instance bandwidth weighting](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configure-bandwidth-weighting.html)).
- **Multi-flow traffic through an internet gateway** [observed]: instances with **less than 32 vCPUs** are "Limited to 5 Gbps". Instances with **more than 32 vCPUs** are "Limited to 50% of the available bandwidth for the instance type". C8in/C8ine/M8in/M8ine/M8idn/R8in/R8idn stay limited to baseline (same page). The doc gives a worked example.

  An `m5.16xlarge` (64 vCPUs, "20 Gbps") can use only 10 Gbps through an internet gateway. **[calculated]** A GB300-class rack node wants to certify multi-Gbps *public* egress. AWS's own model sets the egress ceiling. The ceiling equals min(instance bandwidth, 5 Gbps if <32 vCPU / 50% if >32 vCPU).
- **Single-flow cap, independent of instance size** [observed]: "When instances are not in the same cluster placement group, bandwidth for single-flow traffic is limited to 5 Gbps." AWS defines a single-flow as "a unique 5-tuple TCP or UDP flow" (3-tuple for GRE/IPsec). Documented remedies: a cluster placement group gives up to 10 Gbps single-flow. Multipath TCP (MPTCP) uses multiple paths. ENA Express gives up to 25 Gbps single-flow ([EC2 instance network bandwidth](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)). Note: these remedies all stay intra-AWS.

  None applies to a public-internet path. **[inference]** The 5 Gbps single-flow figure is the best-known vendor precedent for "one TCP stream will not fill a big pipe". rack-bench reuses it directly. It is the reason `bench internet` must aggregate multiple streams to certify egress throughput.
- **Bandwidth specs are "available," not guaranteed** [observed]: "Instance bandwidth specifications apply to both inbound and outbound traffic" but "instances might not achieve this bandwidth; for example, if they exceed network allowances at the instance level, such as packet per second or number of tracked connections" ([same page](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)).

### 1.2 The benchmark methodology AWS ships (knowledge-center runbook, quoted)

The AWS Knowledge Center article "Benchmark network throughput between Linux instances in the same VPC" ([re:Post](https://repost.aws/knowledge-center/network-throughput-benchmark-linux-ec2)) gives AWS's canonical *how to measure* runbook. Its exact methodology [observed]:
1. **Tune placement first**: keep instances close (same AZ > same Region > cross-continent). Use enhanced networking (ENA/ENA Express). Increase MTU and instance size. Launch into a **cluster placement group** for "full-bisection bandwidth and low latency."
2. **Install iperf3**. The runbook gives package-manager commands: RHEL 9 `dnf -y install iperf3`, Ubuntu `apt-get`, CentOS via EPEL, Amazon Linux 2023 `yum -y install iperf3`.
3. **TCP test with parallel streams**: server `sudo iperf3 -s -p 5001`; client `sudo iperf3 -c 172.31.30.41 --parallel 40 -i 1 -t 2`. The published example uses **40 parallel connections** on two `c5n.18xlarge` in a cluster placement group. The example output shows "97.6 Gbits/sec" total across `[SUM]`.

   (Note: the task brief remembers "8 parallel streams". That memory does not match the current article. The current canonical number is 40 streams for 100-Gbps-class instances, `-t 2` for the documented example. [observed, discrepancy noted])
4. **UDP test for loss/jitter**: client `sudo iperf3 -c 172.31.30.41 -u -b 5g`. Example output reports "Jitter (the deviation in time for the periodic arrival of datagrams)" and "Loss and total of UDP datagrams" (0.045% in the example). UDP defaults to 1 Mbps unless `-b` is set. AWS explicitly warns "UDP is connectionless and doesn't have the congestion control algorithms that TCP has". So UDP bandwidth may read lower (same source).
5. The Windows twin article benchmarks with **NTttcp** instead of iperf3. It uses warmup/cooldown phases (`-wu 5 -cd 5 -t 60`). Its XML output includes **`packets_retransmitted`** ([Windows KB](https://repost.aws/knowledge-center/network-throughput-benchmark-windows-ec2)). This is the only place an AWS runbook surfaces a retransmit count.
**[inference]** This is intra-VPC methodology. AWS publishes **no equivalent public-internet throughput benchmark runbook**. The closest is the mtr/traceroute path-troubleshooting set in §1.5.

### 1.3 ENA and ENA Express (single-flow improvements, SRD, MPTCP)

- **ENA Express** raises maximum single-flow bandwidth "from 5 Gbps up to 25 Gbps within the same Region, up to the aggregate instance limit,". It reduces tail latency during congestion. It detects and avoids congested paths. **AWS Scalable Reliable Datagram (SRD)** powers ENA Express. SRD "distributes packets for each network flow across different AWS network paths, and dynamically adjusts distribution when it detects signs of congestion. It also manages packet reordering on the receiving end" ([ENA Express](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-express.html)).

  Requirements: both endpoints run supported instance types with ENA Express enabled. Keep both endpoints in the **same Region**. Keep no middleware boxes in the path (same source). As of May 2026, ENA Express works **between Availability Zones**, "delivering up to 25 Gbps single-flow bandwidth" cross-AZ ([What's New](https://aws.amazon.com/about-aws/whats-new/2026/05/ena-express-availability-zones)).
- AWS's own engineering blog quantifies it: "up to a 93% reduction in P99.9 traffic flow latency and up to a 400% increase in single flow throughput". That means 5× single connection, up to 100 Gbps with nconnect ([ENA Express blog](https://aws.amazon.com/blogs/networking-and-content-delivery/using-ena-express-to-improve-workload-performance-on-aws)).
- **MPTCP** appears in the EC2 bandwidth docs as a customer remedy: "Set up multiple paths between two endpoints to achieve higher bandwidth with Multipath TCP (MPTCP)" ([bandwidth doc](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)). **[inference]** SRD and MPTCP both help only inside AWS's network. AWS documents no improvement mechanism for a Chennai node's public-internet single flows. Parallel streams are the only documented answer.
- **ENA driver metrics** (driver ≥2.2.10 Linux / ≥2.2.2 Windows): read them via `ethtool -S eth0`. The counters include `bw_in_allowance_exceeded`, `bw_out_allowance_exceeded`, `pps_allowance_exceeded`, `conntrack_allowance_exceeded`, `linklocal_allowance_exceeded`, plus `conntrack_allowance_available` (driver ≥2.8.1). On exceeding an allowance, "AWS shapes the traffic that exceeds the maximum by queueing and then dropping network packets" ([Monitor network performance for ENA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-network-performance-ena.html)). Read ENA Express SRD metrics via `ethtool -S eth0 | grep ena_srd`: `ena_srd_mode`, `ena_srd_eligible_tx_pkts`, `ena_srd_tx_pkts`, `ena_srd_rx_pkts`, `ena_srd_resource_utilization` (same source). The same source also documents an egress-fragment PPS limit of **1024 pps** per interface. Override it with ENA Linux driver ≥2.13.3 "fragment proxy mode" (same source).
- **ENSRD/queue tuning**: ENA uses multiple Rx/Tx queues. High-network-performance workloads need multiple ENA queues. Customers configure them per-ENI ([Nitro performance tuning](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-nitro-perf.html)). The ENA Express page references a full "ENA Linux Driver Best Practices and Performance Optimization Guide" on GitHub ([repo](https://github.com/amzn/amzn-drivers)).

### 1.4 MTU guidance: 9001 jumbo inside VPC, 1500 + PMTUD caveats to the internet

- **[observed]** "All EC2 instance types support 1500 MTU". All current-generation instances support jumbo frames (9001 MTU). Hard 1500-byte limits apply to **traffic over an internet gateway**. They also apply to traffic over VPN connections and traffic between AWS Regions (unless transit gateway). Inter-region VPC peering gets 8500 ([Network MTU](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/network_mtu.html)). "Jumbo frames should be used with caution for internet-bound traffic or any traffic that leaves a VPC. Packets are fragmented by intermediate systems, which slows down this traffic."
- **PMTUD blackhole warnings, documented** [observed]: (a) "Path MTU Discovery does not guarantee that jumbo frames will not be dropped by some routers. An internet gateway in your VPC will forward packets up to 1500 bytes only. 1500 MTU packets are recommended for internet traffic" ([Network MTU](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/network_mtu.html)). (b) A network access control list entry can silently block ICMP Type 3 Code 4 ("Destination Unreachable: Fragmentation Needed and Don't Fragment was Set"). AWS documents this: "ICMP traffic can be blocked even if the traffic is allowed at the security group level, such as if you have a network access control list entry that denies ICMP traffic" (same source). The VPC docs tell customers to add an explicit NACL rule for "Destination Unreachable, fragmentation required, and DF flag set (type 3, code 4)" both inbound and outbound. Otherwise "PMTUD [cannot] function correctly and prevent packet loss" ([PMTUD and network ACLs](https://docs.aws.amazon.com/vpc/latest/userguide/path_mtu_discovery.html)).

  (c) AWS's networking blog recommends **PLPMTUD / TCP MTU probing** as an alternate. It does not rely on ICMP ([Improving performance on AWS and hybrid networks](https://aws.amazon.com/blogs/networking-and-content-delivery/improving-performance-on-aws-and-hybrid-networks)). (d) A documented real blackhole case exists: jumbo frames from EC2 to Redshift, where "queries appear to hang and sometimes fail to reach the cluster" ([Redshift troubleshooting](https://docs.aws.amazon.com/redshift/latest/mgmt/troubleshooting-connections.html#connecting-drop-issues)). **[inference]** These four citations are the strongest hyperscaler-published justification for rack-bench having a PMTUD-blackhole probe. The probe sends DF-set pings at 1472+28, plus a TCP-MTU-probe fallback.

### 1.5 Diagnosing a bad internet path: the mtr/traceroute runbooks, and what Reachability Analyzer can't do

AWS's Knowledge Center ships path-diagnosis runbooks with exact commands [observed]:
- **"Troubleshoot network performance issues in Amazon VPC"** ([re:Post](https://repost.aws/knowledge-center/vpc-troubleshoot-network-performance)): "To find latency in your network and determine where delays begin, use traceroute for Linux or tracert for Windows. If My Traceroute (MTR) is available in your environment, then use MTR instead of traceroute." Protocol choice guidance: "If your destination responds to ICMP or you're evaluating a general path, then use ICMP. If your destination doesn't respond to ICMP or your application uses TCP to simulate real traffic, then use TCP." Exact commands: `mtr YOUR_DESTINATION_IP_OR_HOST_NAME -T -P 443 -c 100 --report` (TCP MTR) and `traceroute YOUR_HOST_NAME -T -p 443` (TCP traceroute).
- **"Diagnosing packet loss and latency with MTR"** ([re:Post article](https://repost.aws/articles/ARYuHnu150R9ahMl-2hNNEVw/diagnosing-packet-loss-and-latency-with-mtr)): `sudo mtr -c 100 example-ip --report` (ICMP) and `sudo mtr -T -c 100 example-ip -P port-number --report` (TCP). AWS documents two diagnostic subtleties. **ECMP hashing**: "When you run MTR with TCP or UDP, each new sequence of probes uses an incremented source port. This results in a unique hash for each sequence of probes on ECMP-enabled networks… This makes TCP more effective at detecting issues than ICMP on ECMP networks". **ICMP rate-limit false positives**: some providers rate-limit ICMP. Loss at one hop with 0.0% at subsequent hops indicates rate limiting, not real loss. The [Direct Connect packet-loss KB](https://repost.aws/knowledge-center/direct-connect-packet-loss) states this too.
- **"Troubleshoot issues between VPC and on-premises hosts"** ([re:Post](https://repost.aws/knowledge-center/network-issue-vpc-onprem-ig)) adds **hping3** for end-to-end TCP loss/latency: `hping3 -S -c 50 -V <target>` (SYN packets, 50 count). The reason: "MTRs and traceroute capture per-hop latency. However, hping3 results show packet loss and end-to-end minimum, maximum, and average latency over TCP." The article also instructs: "Before you troubleshoot the issue, it's a best practice to benchmark the performance results" [observed]. This is a measured-not-claimed stance.
- **tcptraceroute** appears in the Direct Connect packet-loss KB: `sudo traceroute -T -p <port>` and a TCP-traceroute install sequence ([Direct Connect packet loss](https://repost.aws/knowledge-center/direct-connect-packet-loss)). The VPN packet-loss KB runs bidirectional MTR from both endpoints ([VPN packet loss](https://repost.aws/knowledge-center/vpn-packet-loss)). It uses `mtr -n -c 200 --report` (ICMP) and `mtr -n -T -P 443 -c 200 -m 60 --report` (TCP, TTL max 60).
- **Reachability Analyzer is configuration-only and VPC-internal** [observed]: "Reachability Analyzer is a static configuration analysis tool… to analyze and debug network reachability between two resources in your VPC." The "How it works" page gives constraints. Source and destination must be **in the same Region**. Location rule: **in the same VPC, or in VPCs connected through a VPC peering connection or a transit gateway**. Resource types are EC2 instances, internet gateways, network interfaces, transit gateways, etc. The tool does not consider BYOIP advertisement state.

  It does not report connectivity due to traffic mirroring ([how Reachability Analyzer works](https://docs.aws.amazon.com/vpc/latest/reachability/how-reachability-analyzer-works.html), [troubleshoot reachability](https://docs.aws.amazon.com/vpc/latest/userguide/reachability-analyzer.html)). **[inference]** The internet gateway can be an *endpoint* of an analysis. But the analysis covers your VPC config, not the internet path beyond it. So AWS offers no equivalent tool for rack-bench's public-path audit. The mtr/traceroute/hping3 runbooks are the published methodology.

### 1.6 Monitoring metrics: CloudWatch vs ENA counters (and the missing retransmit metric)

- **CloudWatch instance metrics** [observed]: `NetworkIn`/`NetworkOut` (bytes, all ENIs, per-minute with detailed monitoring). `NetworkPacketsIn`/`NetworkPacketsOut` (packets, **5-minute periods only**, basic monitoring. PPS = Sum ÷ 300) ([CloudWatch instance metrics](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/viewing_metrics_with_cloudwatch.html)).
- **Microburst caveat, straight from AWS** [observed]: ENA metrics may show an allowance exceeded. They may show packets dropped "while the CloudWatch instance metrics do not… when the instance has a short spike in demand for network resources (known as a microburst), but the CloudWatch metrics are not granular enough to reflect these microsecond spikes" ([bandwidth doc](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)). The KB "Troubleshoot EC2 instances that exceed network limits" adds: "Dropped packets do not count towards CloudWatch's `Network` metrics. Queued packets do count, though, because they eventually go through" ([KB](https://repost.aws/knowledge-center/ec2-instance-exceeding-network-limits)).
- **The CloudWatch agent can export the ENA ethtool counters** as metrics. Configure an `ethtool` section in the agent config (`bw_in_allowance_exceeded`, `bw_out_allowance_exceeded`, `conntrack_allowance_exceeded`, `linklocal_allowance_exceeded`, `pps_allowance_exceeded`) ([Collect network performance metrics](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Agent-network-performance.html)).
- **No retransmit metric** [observed-gap]: neither CloudWatch instance metrics nor ENA driver counters publish TCP retransmissions. The only AWS-runbook-visible retransmit count is NTttcp's XML `packets_retransmitted` field ([Windows KB](https://repost.aws/knowledge-center/network-throughput-benchmark-windows-ec2)). **[inference]** rack-bench's TCP-health retransmit check has no AWS metric to lean on. It must read `ss -ti`/`nstat`/`netstat -s` from the node itself. Google's perfdiag does exactly this (§3.2).

### 1.7 S3 performance guidance: scaling with parallelism, what to measure

- **Per-prefix request-rate baselines** [observed]: "your application can achieve at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix. There are no limits to the number of prefixes in a bucket"; "Amazon S3 doesn't have any limits for the number of connections made to your bucket" ([Best practices design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html), [performance guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)).
- **The scaling doctrine** [observed]: "think of Amazon S3 as a very large distributed system, not as a single network endpoint like a traditional storage server. You can achieve the best performance by issuing multiple concurrent requests to Amazon S3. Spread these requests over separate connections to maximize the accessible bandwidth" (guidelines page). Retry guidance: for >128 MB requests, "retry the slowest 5 percent". For <512 KB requests (median latency "often in the tens of milliseconds"), "retry a GET or PUT operation after 2 seconds" ([design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html)).
- **Measure-first stance** [observed]: "When optimizing performance, look at network throughput, CPU, and DRAM requirements… It's also helpful to look at **DNS lookup time, latency, and data transfer speed using HTTP analysis tools**". Also monitor 503 Slow Down responses. Monitor them via CloudWatch request metrics / S3 Storage Lens / server access logs (guidelines page).
- **Byte-range fetches** support parallel GETs of one object, aligned to multipart part boundaries. S3 **Transfer Acceleration** ships a public browser "Speed Comparison tool". It uploads to regions with/without acceleration ([guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)).
- **No TCP-window math and no single-stream cap number for S3** [observed-gap]. The S3 docs never state a per-stream Mbps figure. This differs from GCS's ecosystem numbers (§3.6). **[inference]** AWS's position: single-stream throughput is a property of *your* path and TCP stack. Their published answer is parallelism, not stream tuning.

## 2. Microsoft Azure — published methodology and the Network Watcher diagnostic suite

### 2.1 The bandwidth model: "expected network bandwidth" Mbps, egress-only enforcement

- **[observed]** "The network bandwidth allocated to each virtual machine is measured on egress (outbound) traffic from the virtual machine. All network traffic leaving the virtual machine is counted toward the allocated limit, regardless of destination… if a virtual machine has a 1,000-Mbps limit, that limit applies whether the outbound traffic is destined for another virtual machine in the same virtual network, or outside of Azure. Ingress isn't measured or limited directly" ([VM network bandwidth](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-machine-network-throughput)). Throughput is per-VM regardless of NIC count, protocol, or destination. **Accelerated networking "doesn't change the limit"** (same source).
- **[observed]** Per-size numbers live in every VM-series doc. They appear as the last column, "Max NICs / Expected network performance (Mbps)" (same source; example tables in the [Q&A](https://learn.microsoft.com/en-us/answers/questions/32629/azure-bandwidth-data-transfer-limit)). Microsoft's own caveat: "Upper limits are not guaranteed, but are intended to provide guidance… Actual network performance will depend on a variety of factors including number of TCP connections, network congestion, application workloads, and network settings" ([Accelerated Networking announcement](https://azure.microsoft.com/en-us/blog/linux-and-windows-networking-performance-enhancements-accelerated-networking)). **[inference]** "Expected, not guaranteed" is Azure's exact wording. A certification suite that turns this into a *measured* number fills the gap Azure itself declares.
- **Flow/connection limits** [observed]: the Azure stack tracks TCP/UDP connections as 5-tuple **flows** (two per connection). It supports at least 500K total connections (500k inbound + 500k outbound flows) for all sizes. Recommended limits scale by vCPU tier. The tier runs from 100K at 2-7 vCPU up to 1M/2M at 64+ (Azure Boost/MANA vs other sizes). Azure warns: "above the recommended limit, connections may be dropped or encounter reduced performance."

  Azure Monitor exposes **Inbound and Outbound Flows** metrics. Microsoft ships the **NCPS tool** (`aka.ms/ncps`) for benchmarking connection performance ([same doc](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-machine-network-throughput)).
- **Accelerated Networking** = SR-IOV (and the Microsoft MANA adapter on Azure Boost sizes) "greatly improving networking performance… lower latency and higher packets per second". Find the required OS list and constraints at [Accelerated networking overview](https://learn.microsoft.com/en-us/azure/virtual-network/accelerated-networking-overview).

### 2.2 The shipped benchmark methodology: NTTCP (300 s), Latte/SockPerf latency, iperf3 in support answers

- **NTTTCP runbook, exact** [observed] ([Test VM network throughput using NTTTCP](https://learn.microsoft.com/en-us/troubleshoot/azure/virtual-network/virtual-network-bandwidth-testing)): use two same-size VMs. Put them in the same proximity placement group or availability set. Receiver: `ntttcp -r -m [<number of VM cores> x 2],*,<receiver IP address> -t 300`. Sender: the same with `-s`. **Run for 300 seconds (5 minutes)**.

  Use `-P 1` single-stream commands first, only "to test configuration". Extend to 300 s "for the most accurate results." Example output reports **Throughput(MB/s)** and, notably, a **Retransmits** column (`60412` retransmits in the example). Cross-OS tests use no-sync mode (`-ns` Windows / `-N` Linux). **[calculated]** The `[cores x 2]` mapping is Azure's rule of thumb for stream count. Example: a 2-core VM gets 4 threads.
- **Latency runbook** [observed] ([Test network latency between Azure VMs](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-test-latency)): use **Latte** (Windows) or **SockPerf** (Linux) instead of ping. The doc's reason: "Tools like Ping use Internet Control Message Protocol (ICMP), which applications don't use. ICMP traffic can be treated differently from application traffic." Exact command: `latte -a <receiver IP>:<port> -i 65100` ("Around 65,000 iterations are enough to return representative results"). The doc's discipline: take **baseline measurements** immediately after deployment. Then re-test after every controlled change and "always compare new test results to the baseline" [observed]. This is the same measured-vs-claimed posture rack-bench needs.
- **iperf3** [observed]: Azure's *official* throughput docs put NTTTCP first. iperf3 appears in Microsoft Q&A support answers for troubleshooting ("On the server side: `iperf3 -s -V`… you can further alter the window sizes and test") ([Q&A: robocopy throughput](https://learn.microsoft.com/en-us/answers/questions/193075/network-throughput-around-100mbps-only-within-tran)). It also appears in the TCP/IP tuning article's test section ([TCP/IP performance tuning](https://docs.azure.cn/en-us/virtual-network/virtual-network-tcpip-performance-tuning)).
- **TCP window math, published by Azure** [observed]. The TCP/IP performance tuning doc tabulates the throughput ceiling of a 64 KiB window at various RTTs. The table: 65,535 B @ 1 ms → 524 Mbps. @ 30 ms → 17.5 Mbps. @ 60 ms → 8.7 Mbps.

  @ 120 ms → 4.4 Mbps. It adds a fiber speed-of-light table (e.g. Beijing–Shanghai 1,080 km → 10.8 ms RTT) ([Azure TCP/IP tuning](https://docs.azure.cn/en-us/virtual-network/virtual-network-tcpip-performance-tuning)). **[inference]** This is the only hyperscaler that ships the TCP-window × RTT table publicly. rack-bench reuses it directly as a theoretical-throughput sanity check. Run this check before flagging a measured number as "bad."

### 2.3 Network Watcher: the diagnostic suite (probe loss/latency with thresholds, packet capture, next hop, IP flow verify, flow logs)

[observed unless noted] Azure's Network Watcher is the most complete *productized* internet-quality diagnostic suite among the three. ([overview](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview), [launch blog](https://azure.microsoft.com/en-us/blog/announcing-azure-network-watcher-network-performance-monitoring-and-diagnostics-service-for-azure)):
1. **Connection Monitor** (the crown piece for rack-bench precedent): it monitors continuously, with agents (Network Watcher extension / Arc agents). It measures "aggregated packet loss and network latency metrics across TCP, ICMP, and HTTP pings" between Azure VMs, **on-prem hosts, URLs, FQDNs, or any IP address**. That is, it explicitly covers internet endpoints ([overview](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview)). Its **state model is threshold-based and published**: Pass = failed-checks% and RTT within thresholds. Fail = exceeded.

   **Warning if observed checks-failed is more than 80% of the threshold**. When you specify no threshold, Azure auto-assigns **750 ms RTT** for TCP/ICMP tests and **10% checks-failed**. Checks: HTTP counts valid response codes. TCP/ICMP compute "packet-loss percentage to determine the percentage of failed checks. To calculate RTT, the service measures the time taken to receive the acknowledgment (ACK)". Traceroute data gives "hop-by-hop loss and latency for your on-premises network." Metrics are `ChecksFailedPercent` and `RoundTripTimeMs`, with dimensions (source, destination, protocol, port…), at 1-minute granularity.

   Topology merges traceroute with an internal next-hop-like logical route (same source).
2. **Packet capture**: on-VM captures with filters (source/dest IP, ports, byte offset). The feature supports Windows and Linux ([launch blog](https://azure.microsoft.com/en-us/blog/announcing-azure-network-watcher-network-performance-monitoring-and-diagnostics-service-for-azure)).
3. **Next hop**: "detect routing issues… provides you with information about the next hop type, IP address, and route table ID for a specific destination IP address" ([overview](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview)).
4. **IP flow verify**: validates allow/deny for a 5-tuple at a VM against NSG + AVNM admin rules. The doc calls it "a quick and simple tool to diagnose connectivity issues to or from other Azure resources, **the internet**, and on-premises" ([IP flow verify](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview)).
5. **Effective security rules / effective routes**, **VPN troubleshoot**, **NSG diagnostics** ([overview](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview). [primer](https://www.nathannellans.com/post/primer-on-azure-network-watcher)).
6. **NSG flow logs**: per-rule traffic telemetry. Microsoft schedules deprecation for 30 September 2027, in favor of VNet flow logs ([cost breakdown](https://www.pump.co/blog/azure-network-watcher)).
**[inference]** Connection Monitor's threshold semantics are the closest thing to a hyperscaler-published *internet-quality grading scale*. Its defaults: 10% checks-failed / 750 ms RTT, warning at 80% of threshold. rack-bench can cite them directly as precedent for its PASS/WARN/FAIL bands.

### 2.4 Azure internet-quality tooling beyond Network Watcher

- **AzureSpeed.com** (community-run, browser-based) offers a per-region **latency test** ("Your browser sends HTTPS requests to Azure storage files in each region. The median latency is calculated"). It offers **download/upload speed tests** ("Each region transfers 100 MiB", run sequentially — "Parallel downloads would divide your local connection… Sequential runs give each region the same opportunity"). It adds a large-file upload test with configurable block sizes, CDN latency, and an **AzCopy Bench** "for servers, automation, and production-scale Azure workloads". Sources: [azurespeed.com](https://www.azurespeed.com/Azure/Latency), [Download](https://www.azurespeed.com/Azure/Download), [Upload](https://www.azurespeed.com/Azure/Upload).

  **[observed with caveat]** AzureSpeed.com is not an official Microsoft Learn doc. Treat it as ecosystem tooling. But its "100 MiB per region, sequential, median latency" methodology is a clean template.
- **Azure Speed Test 2.0** (`azurespeedtest.azurewebsites.net`): measures "latency from your location to the Blob Storage Service in each of the Microsoft Azure Data Centers" ([tool overview](https://www.orhancaliskan.com/en/how-to-identify-the-fastest-azure-region-azure-speed-test)).
- **Azure Network Latency Dashboard** (Portal): region-to-region backbone latency figures (same overview article).
- **`az network watcher` CLI / PowerShell / Terraform** automate connection monitors ([overview](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview)).
**[inference]** Azure's stance: Azure measures and publishes the network *inside* Azure. The *internet* leg is measurable by the customer from Azure sources (agents, azurespeed-style browser probes). Azure ships the probes but not a public-internet SLA.

## 3. Google Cloud — shipped diagnostics (perfdiag/diagnose), egress caps, and Network Intelligence Center

### 3.1 Egress bandwidth caps, including explicit internet-destination caps

[observed] ([Network bandwidth](https://docs.cloud.google.com/compute/docs/network-bandwidth)):
- **"Per-instance maximum egress bandwidth is generally 2 Gbps per vCPU"** for traffic routed within a VPC. (With per-series ceilings: e.g. N2/N2D/C2/C2D 32 Gbps standard / 100 Gbps Tier_1. C3/C3D/C4/C4D/Z3 100/200 Gbps. A4/A3 up to 3,600 Gbps. C4N/M4N 400 Gbps).
- **Egress to destinations OUTSIDE a VPC network (i.e., internet) has its own published caps**. The maximum is the smaller of the per-instance maximum and the caps below. **25 Gbps total with Tier_1 networking enabled**. **7 Gbps total for most series without Tier_1**. G4 gets 7 Gbps at <48 vCPU and 25 Gbps at ≥48 vCPU. Multi-NIC series get 7 Gbps per NIC.

  **H3/H4D: 1 Gbps**. And **"The maximum bandwidth for each unique 5-tuple connection, from a compute instance to a destination outside of a VPC network is 3 Gbps"** (1 Gbps for H3/H4D). The doc gives a worked example. A `c3-standard-44` (32 Gbps max) gets 25 or 7 Gbps to external destinations, depending on Tier_1. GCP also sets a **per-project internet egress bandwidth quota** per region.
- **GCP protects ingress from outside a VPC**. The protection applies at the first of 1,800,000 pps or 30 Gbps per instance. Multi-NIC series get the protection per physical NIC.
- Bandwidth factors can lower actuals. They include VirtIO vs gVNIC, packet size, protocol overhead, and number of flows. They also include TSO/checksum offload settings and network congestion. A 60/40 split applies between Persistent Disk writes and other egress when they compete (same source).
**[inference]** GCP is the only hyperscaler that publishes caps specifically for internet egress. The caps are **per-flow (3 Gbps) and per-instance (7/25 Gbps)**. This is the single most reusable set of "expected" numbers when rack-bench certifies public egress from a VM-shaped node.

### 3.2 gsutil perfdiag — the shipped-diagnostic precedent (now legacy, source-verified)

[observed] The `gsutil perfdiag` command is "provided so that customers can run a known measurement suite when troubleshooting performance problems,". It is the key escalation precedent: "If the Cloud Storage team asks you to run a performance diagnostic please use the following command, and email the output file (output.json) to the @google.com address provided by the Cloud Storage team: `gsutil perfdiag -o output.json gs://your-bucket`" ([perfdiag source](https://github.com/GoogleCloudPlatform/gsutil/blob/master/gslib/commands/perfdiag.py)). The public docs page for perfdiag is retired. It now redirects to the gsutil overview. Reason: "The gsutil tool is a legacy Cloud Storage CLI and minimally maintained" ([gsutil tool](https://cloud.google.com/storage/docs/gsutil/commands/perfdiag) → [redirect](https://cloud.google.com/storage/docs/gsutil/commands/perfdiag)). The command itself still ships in gsutil. Its measurement design, verified from source:
- **Tests**: `lat` runs, for N objects: "write the object, retrieve its metadata, read the object, and finally delete the object. Record the latency of each operation". `rthru`/`wthru` measure read/write throughput with at most C outstanding operations. `rthru_file`/`wthru_file` do the same, but exercise local disk I/O "to gauge the performance impact of the local disk". `list` measures eventual-consistency listing latency. Defaults: `lat`, `rthru`, `wthru`; 5 objects; 1 MiB each; 4 slices; parallelism strategies `fan`/`slice`/`both` (same source).
- **Latency size tiers**: 0 B, 1 KiB, 100 KiB, 1 MiB. Each tier reports Mean, Std Dev, Median, and **90th percentile** in ms (same source).
- **TCP warmup**: perfdiag uploads/downloads a 5 MiB file before throughput tests "to warm up the TCP connection" (same source). **[inference]** rack-bench should copy this. Slow-start confounds any cold-connection throughput measurement.
- **TCP health capture**: perfdiag parses `netstat -s` before and after the run. It reports **TCP segments sent / received / retransmitted during the test** (same source). **[inference]** This is the exact hyperscaler precedent for rack-bench's retransmit metric. No API metric exists anywhere for it. So both Google and rack-bench read the kernel counters.
- **DNS + path sysinfo in the report**: the report includes requester IP. It includes `nslookup -type=CNAME` of the storage endpoint ("googserv_route"). It records resolved endpoint IPs and reverse hostnames. It records **DNS lookup latency** for the Google hostname and TCP connect latency per endpoint IP.

  It records the resolver-observed IP via `o-o.myaddr.google.com`, plus proxy DNS/connect latency. It also records `/proc/sys/net/core/rmem_max`, `wmem_max`, `tcp_timestamps`, `tcp_sack`, `tcp_window_scaling`, CPU count, and load average. It records meminfo, disk counters, and bucket location/storage class (same source). **[inference]** That is a near-complete spec for rack-bench's DNS-health and TCP-tuning-visibility sub-benches, shipped by a vendor.
- **Availability measurement**: perfdiag retries HTTP 5xx itself. It reports "Total HTTP requests made / HTTP 5xx errors / HTTP connections broken / Availability: %" (same source). Availability is a *measured* derived metric, not a claim.

### 3.3 gcloud storage diagnose — the current successor

[observed] `gcloud storage diagnose gs://my-bucket` runs `DOWNLOAD_THROUGHPUT`, `UPLOAD_THROUGHPUT`, and `LATENCY` tests by default against a writable bucket. Billing applies. The tool deletes temp objects on success. Test types: `DIRECT_CONNECTIVITY`, `DOWNLOAD_THROUGHPUT` ("record the number of bytes transferred per second"), `UPLOAD_THROUGHPUT`, `LATENCY` ("Write the objects, retrieve their metadata, read the objects, and record latency of each operation"). It can force download strategies `FILE`/`SLICED`/`STREAMING` and upload strategies `FILE`/`PARALLEL_COMPOSITE`/`STREAMING`.

It controls `--process-count`/`--thread-count`/`--object-count`/`--object-size`. And **`--export --destination` bundles gcloud logs + diagnose output + `gcloud info --anonymize` into a .tar.gz diagnostic bundle** for sharing. The doc cautions: the bundle contains system information ([gcloud storage diagnose reference](https://docs.cloud.google.com/sdk/gcloud/reference/storage/diagnose)). The report includes "system information like free memory, available CPU, average CPU load per test, disk counter deltas and diagnostic information specific to individual tests" (same source). **[inference]** The `--export` bundle is the escalation artifact rack-bench should mirror (certification evidence pack).

### 3.4 Network Intelligence Center: Performance Dashboard (incl. internet traffic types), Network Analyzer, Cloud Network Insights

- **Performance Dashboard** [observed]: it collects agentless metrics automatically, for two traffic types. Type one: "Latency metrics for each possible Google Cloud zone pair". Type two: **"Latency metrics between regions where you have virtual machine (VM) instances and end devices on the internet that communicate with the VMs"** ([View Google Cloud latency dashboard](https://docs.cloud.google.com/network-intelligence-center/docs/performance-dashboard/how-to/view-google-cloud-latency)). The **"To the internet"** traffic type shows "the median round-trip time (RTT) between selected geographic areas and regions that contain VM instances,". Filter it by Network Service Tier (Standard vs Premium). Views: Table/Map/Timeline (same source).

  Packet-loss views exist for cross-zonal traffic: a heatmap of "average packet loss between zone pairs" with a bidirectional per-pair graph ([packet loss dashboard](https://docs.cloud.google.com/network-intelligence-center/docs/performance-dashboard/how-to/view-google-cloud-packet-loss)). Project-specific variants also exist. **[inference]** This is passive, aggregate measurement of Google↔internet RTT. Google publishes measured internet-leg latency by geography (a measured-not-claimed precedent). But it is not a per-customer certification of your path.
- **Network Analyzer** [observed]: it "runs continuously and triggers relevant analyses based on near real-time configuration updates… If a network failure is detected, it tries to correlate the failure with recent configuration changes to identify root causes". It gives insights on topology, firewall rules, routes, dependencies, and connectivity to services ([overview](https://docs.cloud.google.com/network-intelligence-center/docs/network-analyzer/overview), [blog](https://cloud.google.com/blog/products/networking/introducing-network-analyzer-detect-service-and-network-issues)).
- **Cloud Network Insights** (via Network Intelligence Center) [observed]: the page says, "Gain end-to-end network and web performance visibility across hybrid/multicloud environments. Cloud Network Insights monitors connectivity 24/7 to pinpoint bottlenecks in **Google Cloud, third-party clouds, and ISPs, even without user traffic**. Visualize hop-by-hop paths, validate SLAs, and differentiate network from application latency" ([Network Intelligence Center](https://cloud.google.com/network-intelligence-center)). **[inference]** This is active synthetic probing to ISPs. It has the same shape as rack-bench's `bench internet` path audit.
- **Connectivity Tests / Flow Analyzer** also live in the same center ([NIC page](https://cloud.google.com/network-intelligence-center)).
- **Chennai context** [observed]: Google publishes an edge-cache presence in Chennai. The Media CDN cache locations list includes "Chennai, India". Mumbai and Delhi host Google Cloud regions ([Media CDN locations](https://docs.cloud.google.com/media-cdn/docs/locations)). **[inference]** Google-side anycast/edge endpoints in Chennai make the shortest-RTT public targets. The targets are GCS and Google endpoints for a Chennai rack-bench node. Encode them as bench targets.

### 3.5 TCP optimization and latency-measurement guidance

- [observed] Google's TCP optimization doc recommends socket-buffer ceilings for long/RTT paths: `net.core.rmem_max`/`wmem_max` = **4 MB**. It says "default to 4 MB" on Linux ≥6.18. For earlier kernels, it says "we recommend increasing these limits to 4 MB on modern platforms". Pair them with `tcp_rmem`/`tcp_wmem` autotuning arrays. The limits exist "to avoid… OOM conditions… little risk in increasing these limits" unless connection counts are in the millions ([TCP optimization](https://docs.cloud.google.com/compute/docs/networking/tcp-optimization-for-network-performance-in-gcp-and-hybrid)).
- [observed] Google's own latency methodology: "we recommend using netperf over ping for latency tests… we prefer using TCP over ICMP. TCP is a more common use case and thus tends to be more representative of real-world applications". Measure RTT via `netperf -H <ip> -t TCP_RR -- -o min_latency,max_latency,mean_latency`. The blog acknowledges ping (`ping <ip> -c 100`) and TCP-based ping variants (nping/hping/TCPing). It names PerfKit Benchmarker as Google's benchmarking harness ([Using netperf and ping to measure network latency](https://cloud.google.com/blog/products/networking/using-netperf-and-ping-to-measure-network-latency)). (Note: Google Cloud docs do not verify a standalone Google tool literally named "noping". The blog references *nping*; see Gaps.)
- [observed] The [network bandwidth](https://docs.cloud.google.com/compute/docs/network-bandwidth) doc documents gVNIC vs VirtIO and MTU up to **8896** in VPC. It also documents queue-count allocation formulas per vCPU/NIC and Tier_1 enablement (`--network-performance-configs=total-egress-bandwidth-tier=TIER_1`).

### 3.6 Cloud Storage performance guidance (per-stream and parallelism)

- [observed] Google's Performance Atlas post says: "Cloud Storage is extremely strong in terms of single-stream throughput… for both uploads and downloads, Cloud Storage performance is at its best for larger requests of around 1MB in size. If you have to use smaller requests, try to parallelize them". Per-request fixed transactional overhead dominates small objects. gsutil defaults to 4 download threads. It can do sliced (HTTP Range GET) downloads and parallel composite uploads. And the reusable stance: "you can't fix what you can't measure. As such, it's important to establish a baseline expectation… we suggest running the perfdiag utility which runs a set of tests to report the actual performance of a Cloud Storage bucket" ([Performance Atlas blog](https://cloud.google.com/blog/products/gcp/optimizing-your-cloud-storage-performance-google-cloud-performance-atlas)).
- [observed, third-party] Community measurement pegs single-stream GCS at **>200 MiB/s per transfer request** ("GCS is highly performant and delivers over 200 MiB/s streaming per transfer request for uploads or downloads. Greater throughput requires parallelization"). Serial download throughput stays insensitive to vCPU count. Parallel streams achieve 8 GiB/s+ ([beginswithdata.com](https://www.beginswithdata.com/2024/02/01/google-cloud-storage-max-throughput)). **[observed-gap]** No current official Google doc publishes a hard per-stream Mbps number for GCS. The old `cloud.google.com/storage/docs/performance` URL now 404s. **[inference]** Treat "~200 MiB/s ≈ 1.6–1.7 Gbps per stream" as an empirically stable ceiling from third-party data, not a vendor SLA.
- [observed] Backblaze's independent Q1-2026 cloud-storage benchmark shows the feasibility of an external, repeatable cross-provider suite. The suite measures object-store throughput ([Backblaze stats](https://finance.yahoo.com/sectors/technology/articles/backblaze-publishes-q1-2026-performance-130000137.html)). It publishes methodology and raw data. Its multi-threaded 256 KiB uploads spread 24–164 MiB/s across providers, with per-region variation.

## 4. Cross-cutting: what they refuse to certify for the public internet, and what support asks customers to measure

### 4.1 The documented per-provider boundary

- **AWS** [observed/inference]: all performance *numbers* (bandwidth, burst, 5 Gbps single-flow) describe instance-to-instance or instance-to-AWS-service paths. Internet-gateway traffic gets derated multi-flow caps and a 1500-byte MTU limit. Reachability Analyzer stops at VPC-internal config analysis. The only internet-path methodology AWS publishes is the mtr/traceroute/hping3 *troubleshooting* runbooks ([bandwidth](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html), [MTU](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/network_mtu.html), [reachability](https://docs.aws.amazon.com/vpc/latest/reachability/how-reachability-analyzer-works.html), [KB](https://repost.aws/knowledge-center/vpc-troubleshoot-network-performance)). This research finds no published internet-path throughput/latency/loss SLA for ordinary VMs.
- **Azure** [observed/inference]: "expected network bandwidth… upper limits are not guaranteed" — even intra-Azure. *Customer-operated* probes cover the internet leg (Connection Monitor agents probing URLs/IPs; azurespeed-style tests) ([VM bandwidth](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-machine-network-throughput), [announcement](https://azure.microsoft.com/en-us/blog/linux-and-windows-networking-performance-enhancements-accelerated-networking)).
- **Google Cloud** [observed/inference]: it publishes measured aggregate Google↔internet median RTT (Performance Dashboard "To the internet"). It also publishes hard internet-egress caps (3 Gbps/flow; 7/25 Gbps/instance). But these are fleet facts and quotas, not customer-path certifications ([latency dashboard](https://docs.cloud.google.com/network-intelligence-center/docs/performance-dashboard/how-to/view-google-cloud-latency), [network bandwidth](https://docs.cloud.google.com/compute/docs/network-bandwidth)).
- **Common pattern [inference]:** every hyperscaler's numbers take one of three forms. (a) Intra-cloud guarantees. (b) Instance-level *allowances* (caps, not floors). (c) Fleet-aggregate measurements. **None publishes a methodology or threshold for certifying one node's north-south internet quality**. That is the empty space rack-bench's `bench internet` occupies.

### 4.2 Support-escalation asks: exact commands from public runbooks

- **AWS** [observed]: the runbooks ask for bidirectional MTR. They also ask for TCP-MTR to port 443, TCP traceroute, and hping3 SYN floods of 50. Commands: `mtr -n -c 200 --report` / `mtr -n -T -P 443 -c 200 -m 60 --report` / `traceroute -T -p 443` / `hping3 -S -c 50 -V <ip>` ([VPN packet loss](https://repost.aws/knowledge-center/vpn-packet-loss), [Direct Connect packet loss](https://repost.aws/knowledge-center/direct-connect-packet-loss), [VPC↔on-prem](https://repost.aws/knowledge-center/network-issue-vpc-onprem-ig)). The Direct Connect KB says: "check the MTR results… If the subsequent hop shows a loss of 0.0%, this can indicate ICMP rate limiting".
- **Azure** [observed]: the runbooks ask for NTTCP 300-second runs from both endpoints. They ask for Latte/SockPerf 65k-iteration RTT runs. Take baselines *before* incidents ([NTTTCP](https://learn.microsoft.com/en-us/troubleshoot/azure/virtual-network/virtual-network-bandwidth-testing), [latency](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-test-latency)). Q&A support answers add iperf3 server/client commands with window-size variation ([Q&A](https://learn.microsoft.com/en-us/answers/questions/193075/network-throughput-around-100mbps-only-within-tran)).
- **Google Cloud** [observed]: email the `gsutil perfdiag -o output.json gs://your-bucket` output to the Cloud Storage team (legacy) ([perfdiag source](https://github.com/GoogleCloudPlatform/gsutil/blob/master/gslib/commands/perfdiag.py)). Send the `gcloud storage diagnose gs://my-bucket --export --destination=<path>` bundle (current) ([diagnose reference](https://docs.cloud.google.com/sdk/gcloud/reference/storage/diagnose)).
**[inference]** All three vendors, when diagnosing, ask the customer to *run a defined measurement from the customer side*. Support escalation is measurement-first, vendor-claim-second. This is precisely the rack-bench PASS philosophy, already institutionally validated.

### 4.3 Throughput to their object stores from outside

- **AWS S3** [observed]: no connection limits. Scale with parallel connections + byte-range fetches. Measure with HTTP analysis tools. Monitor 503s. Per-prefix baselines: 3,500/5,500 rps ([guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html), [design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html)).
- **GCS** [observed]: strong single-stream for ~1 MiB+ requests. Parallelize small requests. Use perfdiag/diagnose as the official measurement suite ([Performance Atlas](https://cloud.google.com/blog/products/gcp/optimizing-your-cloud-storage-performance-google-cloud-performance-atlas)). Third-party data gives ~200 MiB/s/stream ([beginswithdata](https://www.beginswithdata.com/2024/02/01/google-cloud-storage-max-throughput)).
- **Azure Blob** [observed, adjacent]: Microsoft publishes per-account scalability targets (e.g. standard general-purpose v2 ingress/egress limits) as account-level caps. They are not stream guidance ([scalability targets](https://learn.microsoft.com/en-us/azure/storage/common/scalability-targets-standard-account)). The brief includes this item for symmetry. rack-bench should treat Azure Blob targets as account-level, not per-stream, limits.
**[inference]** A rack-bench object-store bench should certify **aggregate** egress/ingress with N parallel streams (the universal vendor answer). It should report single-stream as a *separate, informational* metric. It should always run a TCP warmup before timing (perfdiag precedent).

## 5. What rack-bench can directly reuse from hyperscaler methodology

1. **Expected-value anchors (all published):** AWS caps internet egress at 5 Gbps for <32-vCPU instances. It derates >32-vCPU instances by 50%. The single-flow cap is 5 Gbps ([EC2 doc](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html)).

   GCP gives 3 Gbps per internet flow, 7/25 Gbps per instance, and 1.8M pps/30 Gbps ingress protection ([network bandwidth](https://docs.cloud.google.com/compute/docs/network-bandwidth)). Azure publishes expected-bandwidth Mbps per size ([VM bandwidth](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-machine-network-throughput)). These numbers give defensible "is the measured number sane?" bands for a VM-shaped node.
2. **Threshold semantics:** Azure Connection Monitor's published defaults are 750 ms RTT, 10% checks-failed, and Warning at >80% of threshold. Use them as a template for rack-bench PASS/WARN/FAIL banding ([Connection Monitor](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview)).
3. **The TCP-window × RTT table** from Azure's tuning doc serves for theoretical-max sanity checks ([TCP/IP tuning](https://docs.azure.cn/en-us/virtual-network/virtual-network-tcpip-performance-tuning)). GCP's 4 MB rmem/wmem guidance serves for long paths ([TCP optimization](https://docs.cloud.google.com/compute/docs/networking/tcp-optimization-for-network-performance-in-gcp-and-hybrid)).
4. **Tools the vendors themselves use/endorse:** iperf3 (TCP `-P`/parallel + UDP `-b` loss/jitter) with cluster/placement-group discipline ([AWS KB](https://repost.aws/knowledge-center/network-throughput-benchmark-linux-ec2)). NTTCP with 300 s duration, `[cores×2]` streams, warmup/cooldown, retransmit output ([Azure KB](https://learn.microsoft.com/en-us/troubleshoot/azure/virtual-network/virtual-network-bandwidth-testing)). Latte/SockPerf ~65k-iteration RTT over ICMP ([Azure latency KB](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-test-latency)). netperf TCP_RR over ping ([Google blog](https://cloud.google.com/blog/products/networking/using-netperf-and-ping-to-measure-network-latency)). mtr ICMP+TCP with `-c 100/200 --report`, tcptraceroute to 443, and hping3 for end-to-end TCP loss ([AWS KBs](https://repost.aws/knowledge-center/vpc-troubleshoot-network-performance)).
5. **The perfdiag test matrix as a spec:** it specifies size-tiered latency (0/1 KiB/100 KiB/1 MiB; mean/median/stdev/p90). It specifies read+write throughput with and without disk I/O, and TCP warmup before timing. It captures `netstat -s` retransmit deltas, DNS endpoint-resolution latency + connect latency, and sysinfo (rmem/wmem/window_scaling). It derives availability % from 5xx counts, with JSON output for escalation ([perfdiag source](https://github.com/GoogleCloudPlatform/gsutil/blob/master/gslib/commands/perfdiag.py)). Add `gcloud storage diagnose`'s FILE/SLICED/STREAMING strategy matrix and `--export` evidence bundle ([reference](https://docs.cloud.google.com/sdk/gcloud/reference/storage/diagnose)).
6. **PMTUD blackhole probes:** AWS documents these caveats: an IGW forwards ≤1500. NACLs can silently drop ICMP type-3/code-4. PLPMTUD/TCP-MTU-probing serves as fallback. A real hang case exists with Redshift. Together they justify a DF-ping size sweep + TCP-MTU-probe sub-bench ([network_mtu](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/network_mtu.html), [PMTUD and NACLs](https://docs.aws.amazon.com/vpc/latest/userguide/path_mtu_discovery.html), [hybrid networks blog](https://aws.amazon.com/blogs/networking-and-content-delivery/improving-performance-on-aws-and-hybrid-networks)).
7. **Loss-diagnosis craft:** ECMP-aware TCP-based MTR increments source ports, so each probe hashes differently. The ICMP-rate-limit false-positive rule: loss at hop N with 0.0% downstream = rate limiting, not real loss. AWS documents both ([MTR article](https://repost.aws/articles/ARYuHnu150R9ahMl-2hNNEVw/diagnosing-packet-loss-and-latency-with-mtr), [DX KB](https://repost.aws/knowledge-center/direct-connect-packet-loss)).
8. **Microburst-aware sampling:** AWS itself warns that 1-minute CloudWatch can miss microsecond-scale allowance drops ([bandwidth doc](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html), [limits KB](https://repost.aws/knowledge-center/ec2-instance-exceeding-network-limits)). So rack-bench must sample counters at sub-second resolution during its 2-hour window. It must not rely on coarse vendor metrics.
9. **Object-store bench design:** certify parallel streams + range GETs as the aggregate number (AWS S3 + GCS doctrine). Report single-stream as informational (~200 MiB/s GCS empirical). Report p50/p90 latency per size tier. Count 503/5xx as availability. Use 100 MiB-per-target sequential runs as a fair comparison protocol (azurespeed precedent) ([S3 guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html), [Performance Atlas](https://cloud.google.com/blog/products/gcp/optimizing-your-cloud-storage-performance-google-cloud-performance-atlas), [azurespeed](https://www.azurespeed.com/Azure/Download)).
10. **What NOT to reuse:** any number as a guarantee. Every hyperscaler explicitly disclaims ("up to", "expected, not guaranteed", "maximum possible… not a guarantee"). So rack-bench's PASS must remain measurement-only. Use vendor numbers only as sanity bands ([EC2](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html), [Azure](https://azure.microsoft.com/en-us/blog/linux-and-windows-networking-performance-enhancements-accelerated-networking), [GCP](https://docs.cloud.google.com/compute/docs/network-bandwidth)).

## Gaps

1. **No hyperscaler publishes a public-internet path SLA or certification methodology**. The review of all docs confirms this by absence.
