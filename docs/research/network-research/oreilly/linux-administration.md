## 4. Portable techniques (3–5)

1. [inference] **Host identity and baseline check:** check host identity and baseline before you put blame on the fabric. Make a record of OS/kernel, NIC/device and interface/port mapping, addresses, link state, and selected route for each test host. Keep this as portable administration practice, not a claim of exact-checklist prescription by the book. NCCL troubleshooting also checks RDMA device/link status. [Packt Ch. 1–2 TOC](https://www.packtpub.com/en-TW/product/mastering-linux-network-administration-9781784399597/chapter/preface-pref/section/what-this-book-covers-preflvl1sec02) [NCCL troubleshooting](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/networking_troubleshooting.html)
2. [inference] **Check routing and topology as distinct from throughput.** Check host routes/interfaces and the intended peer path. Host route inspection does not show switch forwarding, adaptive routing, or rail use. Chapter 8 TOC shows only general routing/QoS relevance. [Packt Ch. 8 TOC](https://www.packtpub.com/en-us/product/mastering-linux-network-administration-9781784399597/chapter/8-understanding-advanced-networking-concepts-8/section/routing-tcpip-traffic-ch08lvl1sec61) [NCCL troubleshooting](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/networking_troubleshooting.html)
3. [inference] **Host-resource/network bottleneck separation:** keep host-resource bottlenecks separate from network bottlenecks. Check host CPU/memory/resource pressure with per-rail RDMA and NCCL goodput during a representative test. Keep the book's monitoring chapter as conceptual support only. Do not make link line rate the same as achieved collective bandwidth. [Packt Ch. 5 TOC](https://www.packtpub.com/en-in/product/mastering-linux-network-administration-9781784399597/chapter/5-monitoring-system-resources-5/section/maintaining-log-size-with-logrotate-ch05lvl1sec41) [NCCL tests](https://github.com/NVIDIA/nccl-tests)
4. [inference] **Reachability/security check separation:** keep reachability/security checks separate from data-plane pass criteria. SSH access and service/firewall configuration can show the cause of management or bootstrap failures. But successful SSH does not show RDMA health. Run tests on actual verbs and NCCL paths. [O'Reilly Ch. 3 TOC](https://learning.oreilly.com/library/view/mastering-linux-network/9781784399597/ch03.html) [NCCL troubleshooting](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2312/user-guide/docs/troubleshooting/networking_troubleshooting.html)
5. [inference] **Historical command examples:** keep historical commands as examples, not certification instructions. This 2015 book puts its date before GB300, modern NCCL, and contemporary RDMA stacks. Check command availability and semantics against deployed distro/tool versions; use current `ip`/`ss` and version-matched RDMA/NCCL documentation. Do not make blind copies of legacy `ifconfig`, `route`, `netstat`, distro service or firewall workflows. Keep this as a version-safety warning, not a claim that the book shows each named command.
