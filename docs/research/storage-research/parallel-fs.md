# Parallel / Shared Filesystems at Rack Scale: Failure Modes & Benchmark Practice

Research brief for rack-scale (64–512 client node) storage certification. Sources: Lustre/OpenSFS/DDN, IBM Storage Scale (GPFS), WEKA, VAST Data, Ceph (Red Hat + ceph.io), JuiceFS, NetApp NFSv4/pNFS, Hammerspace, Spectra, and HPC production sites (ALCF/Polaris, OLCF/Frontier, TACC). Every claim carries its source URL.

---

## 1. Client-side pathologies at 64–512 node scale

### 1.1 Metadata server (MDS) storms

- **One shared directory = MDS meltdown.** Lustre user-guide best practice (INCD, Portugal): "Writing thousands of files to a single directory produces massive load on Lustre metadata servers, often resulting on taking filesystems offline"; opening a file keeps a lock on the parent directory, so many opens in one directory create contention. [https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices](https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices)
- **`ls -l` is a cross-server RPC storm.** File size lives on the OSTs, ownership on the MDT, so `ls -l` fires RPCs to MDS *and* every OSS for each file — very costly with many files/directories. Same guidance repeated by NASA HECC and UMBC. [https://hpcf.umbc.edu/general-productivity/lustre-best-practices](https://hpcf.umbc.edu/general-productivity/lustre-best-practices), [https://www.nas.nasa.gov/hecc/support/kb/lustre-best-practices_226.html](https://www.nas.nasa.gov/hecc/support/kb/lustre-best-practices_226.html)
- **Lock memory scales as clients × files.** Lustre wiki: every client that accesses a file needs a ~1 KB lock; 1,000 clients × 1,000 files ≈ 1 GiB of MDS RAM just for locks; target 10–20% of namespace as active working set in cache. MDT I/O is small, random, transactional (OLTP-like). [https://wiki.lustre.org/Lustre_Metadata_Service_(MDS)](https://wiki.lustre.org/Lustre_Metadata_Service_(MDS))
- **CephFS MDS is largely single-threaded per daemon and cache-sensitive.** croit's IO500 run: during the full 300 s mdtest the MDS emitted `MDSs behind on trimming`, `MDSs report oversized cache`, `Clients failing to respond to cache pressure` health warnings, and mdtest-easy-stat collapsed from ~31 kIOPS (short run) to **0.866 kIOPS (~36× collapse)**; raising `mds cache memory limit` from 1 GB to 12 GB restored ~44 kIOPS. Active MDS CPU pinned at 100% (single-threaded hot path). [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
- **Ceph's official answer is multiple active MDS ranks** (metadata sharded across active MDS daemons; IBM/Red Hat docs describe active-active MDS scaling and standby failover). [https://www.ibm.com/docs/en/storage-ceph/8.1.0?topic=systems-cephfs-features-enhancements](https://www.ibm.com/docs/en/storage-ceph/8.1.0?topic=systems-cephfs-features-enhancements), [https://docs.ceph.com/en/nautilus/cephfs/add-remove-mds/](https://docs.ceph.com/en/nautilus/cephfs/add-remove-mds/)
- **Lustre separates data and metadata precisely to avoid this, but the MDS is still the classic bottleneck** for small-file workloads (WEKA's architecture explainer). [https://www.weka.io/learn/lustre-file-system-explained](https://www.weka.io/learn/lustre-file-system-explained)
- **Directory-size cap as a first-class perf knob:** AWS FSx for Lustre tells users to keep directories under 100K files to cut parent-directory lock acquisition time, and ships client tunings (`llite.*.statahead_xattr=1`; older revisions: `ldlm.namespaces.*.lru_size=<100 × CPUs>`, `lru_max_age=600000`) that must be re-applied by boot cron because they don't persist. [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)
- **Timeout/eviction storms at scale:** Lustre's timeout hierarchy (LND/PtlRPC/lock-waiting timeout) exists specifically to avoid client eviction when blocking callbacks are ignored; mis-tuned defaults "not correct for all" systems (Stanford SRCC / Lustre engineering talk). [https://srcc.stanford.edu/sites/g/files/sbiybj25536/files/media/file/lustre_timeout_hierarchy.pdf](https://srcc.stanford.edu/sites/g/files/sbiybj25536/files/media/file/lustre_timeout_hierarchy.pdf)

### 1.2 Lock / token conversion thrash (shared-file & append patterns)

- **GPFS: parallel appends to one file serialize on the write token.** GPFS user-group mailing list (Jump Trading): with concurrent appended writes to the same file, "one node at a time can write to roughly the same position… a write_lock token has to be revoked on the node that currently owns the token, then given to one of the other nodes" — token management overhead on nearly every write. Fix: non-overlapping byte ranges per node (byte-range tokens), which GPFS handles without blocking. [https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html](https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html)
- **GPFS: a stuck token can hang the whole cluster.** Storage Scale user-group network-topics deck: "if one node gets the token for an important resource (say a write token for the root directory)… this can lead to a cluster-wide hang if the node fails to release that token"; threads that can't get tokens/locks "effectively appear to be hung." [https://www.spectrumscaleug.org/wp-content/uploads/2025/04/SSUG24NYC11-Storage-Scale-Network-Topics-NYC.pdf](https://www.spectrumscaleug.org/wp-content/uploads/2025/04/SSUG24NYC11-Storage-Scale-Network-Topics-NYC.pdf)
- **GPFS deadlock detection and waiters as the diagnostic.** NERSC GPFS troubleshooting guide: `mmdiag waiters`, `ClientToken::Acquire` / `ClientRangeToken::Acquire` waiter reasons; IO completion times > 2–3 s are "a definite sign of trouble"; `deadlockDetectionThreshold` defaults to 300 s. [https://www.spectrumscale.org/wp-content/uploads/2017/12/NERSC/GPFS-Troubleshooting-Apr-2017.pdf](https://www.spectrumscale.org/wp-content/uploads/2017/12/NERSC/GPFS-Troubleshooting-Apr-2017.pdf)
- **Lustre shared-file writes: lock handoff caps throughput.** CUG-2017 lockahead paper: for shared-file tests, performance is "typically 20% and not better than 65% of file-per-process performance"; a client usually gets only 2–4 blocks (at 1 MiB) before handing the LDLM extent lock back. Hence `lfs ladvise -a lockahead` (Lustre 2.9+) lets apps pre-acquire extent locks; group locks let many clients opt out of LDLM contention entirely. [https://cug.org/proceedings/cug2017_proceedings/includes/files/pap141s2-file1.pdf](https://cug.org/proceedings/cug2017_proceedings/includes/files/pap141s2-file1.pdf), [https://doc.lustre.org/lustre_manual.xhtml](https://doc.lustre.org/lustre_manual.xhtml), [https://www.youtube.com/watch?v=ITfZfV5QzIs](https://www.youtube.com/watch?v=ITfZfV5QzIs)
- **Same-file-region access from many clients degrades coherently but slowly** (INCD best practices: "many processes trying to access the same file region simultaneously can cause performance degradation"). [https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices](https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices)
- **CephFS hard shared-file writes go atomic.** croit's IO500 analysis: ior-hard makes every 47008-byte write a partial modification of a RADOS object previously touched by another client, "and therefore the write has to be performed atomically" — the phase is latency-bound, not bandwidth-bound (0.38 GiB/s hard vs ~13 GiB/s easy on the same cluster). [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
- **JuiceFS pushes the same class of problem into the metadata engine:** all metadata ops are transactional KV/SQL ops; Redis is ~2–4× faster than MySQL for pure metadata, and the engine choice dominates small-file performance (write small file: ~95–109 files/s Redis vs ~82 files/s MySQL in their published bench). [https://juicefs.com/docs/community/metadata_engines_benchmark](https://juicefs.com/docs/community/metadata_engines_benchmark)

### 1.3 Eager cache-coherence stalls

- **Lustre provides *complete* cache coherence — and pays for it.** Lustre FAQ: "Complete cache coherence is provided for both metadata… and file data. Clients and servers both take locks with a distributed lock management service; caches are flushed before locks are released." [https://wiki.lustre.org/Frequently_Asked_Questions](https://wiki.lustre.org/Frequently_Asked_Questions)
- **Client cache caps at scale are a real tuning surface:** FSx/Lustre recommends `ldlm.namespaces.*.lru_size ≈ 100 × CPUs` and `lru_max_age=600000` for clients with >64 GiB RAM (older revision of the same doc); stale-parameter persistence is a classic source of "the benchmark ran great once." [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)
- **Async/buffered client writes trade consistency for speed** — AWS explicitly warns the request model "has tradeoffs in consistency (if you're using multiple EC2 instances) and speed." [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)
- **NFSv3 cannot safely use Linux client caches** (no coherency): WEKA states NFSv3 "does not support coherency so utilizing Linux caching can lead to data inconsistency for read cache and potential data corruption for write cache," while their client's adaptive caching keeps page-cache/dentry-cache benefits with cluster-wide coherency. [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access)
- **Client metadata writeback caching is an active Lustre R&D area** (WBC/"MemFS" with exclusive LDLM locks, batched & delayed metadata flush — CLUG 2021 talk) precisely because eager coherence is the metadata bottleneck. [http://lustrefs.cn/wp-content/uploads/2022/02/CLUG2021_%E5%88%98%E8%8E%B9_Lustre%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F%E7%9A%84%E5%AE%A2%E6%88%B7%E7%AB%AF%E5%85%83%E6%95%B0%E6%8D%AE%E5%9B%9E%E5%86%99%E7%BC%93%E5%AD%98.pdf](http://lustrefs.cn/wp-content/uploads/2022/02/CLUG2021_%E5%88%98%E8%8E%B9_Lustre%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F%E7%9A%84%E5%AE%A2%E6%88%B7%E7%AB%AF%E5%85%83%E6%95%B0%E6%8D%AE%E5%9B%9E%E5%86%99%E7%BC%93%E5%AD%98.pdf)

### 1.4 Single-client TCP constraint

- **Default Linux NFS mount = one TCP socket ≈ 2 GB/s ceiling.** VAST KB: "This default mount configuration sets up a single TCP connection… performance of the connection is limited by the use of a single TCP socket on the client side and a single storage port… typically around 2 GBps." [https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1](https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1)
- **Mitigations, quantified by VAST:** `nconnect` (≤16 TCP connections, up to ~7 GB/s, IOPS unchanged since one CNode serves); NFSoRDMA (~9 GB/s single connection); Multipath across CNodes (demonstrated 162 GB/s from a DGX with VAST-NFS client); to saturate 100G: `nconnect=4` RDMA or `nconnect=8` TCP. [https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1](https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1)
- **WEKA measured it head-to-head:** NFSv3 with `nconnect=16` on one HDR IB client delivered 1.6 GiB/s vs 12.3 GiB/s (7.5×) for their client on the same backend; for 4K random reads 52.4 kIOPS vs 727 kIOPS (13×), with ~2× lower CPU per unit of work — and note NFS+`nconnect` still only used one server-side path. [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access)
- **NFS rsize/wsize negotiation quietly caps you:** client-set 1 MiB values are negotiated down to what the server supports (NFSv4 default 32 KiB) — a classic "why is my benchmark 16× off" trap. [https://www.enterprisestorageforum.com/management/nfs-vs-parallel-file-system-performance-analysis](https://www.enterprisestorageforum.com/management/nfs-vs-parallel-file-system-performance-analysis)
- **Same story on the Ceph side:** a single CephFS kernel client tops out at ~6 GiB/s read/write in CERN's high-density evaluation; throughput then scales linearly with the number of clients until the cluster's aggregate ceiling (6 of 8 client nodes saturate the backend). [https://cds.cern.ch/record/2790637/files/document.pdf](https://cds.cern.ch/record/2790637/files/document.pdf)
- **A single cephfs mount shares one flush kworker** — croit found `kworker/u194:0+flush-ceph` eating 70–80% of a client CPU and fixed it with multiple mounts (`noshare`) / LXC containers, because IO500 only uses one mountpoint per host. [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)

### 1.5 Small-IO death

- **Per-operation round trips dominate:** FSx/Lustre docs — every file op pays a client↔server round trip, so throughput rises with average I/O size (overhead amortization); small random I/O against cold tiers needs much higher concurrency. [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)
- **4K random IOPS is where protocol overhead shows:** WEKA's fio profile (libaio, `direct=1`, `iodepth=8`, `bs=4k randread`) put NFS+nconnect at 52.4 kIOPS vs 727 kIOPS for their client — the gap is stack + single-path overhead, not media. [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access)
- **The IO500 "hard" I/O (47,008-byte unaligned, strided single-shared-file) is the standard small-IO stressor** — Glenn Klockwood notes it is IOPS-limited on most systems yet scored as GiB/s, deliberately penalizing systems that can't handle unaligned-but-consistent access. [https://www.glennklockwood.com/garden/io500](https://www.glennklockwood.com/garden/io500)
- **AI workloads are bimodal:** small random reads during data loading + large sequential writes during checkpointing — most legacy systems optimize one, not both (WEKA). [https://www.weka.io/learn/ai-storage-for-training](https://www.weka.io/learn/ai-storage-for-training)
- **Raw-IOPS numbers mislead because of caching:** Glenn Klockwood's all-flash study — random-write IOPS roughly halve under `O_DIRECT` vs buffered, and buffered numbers reflect write-back cache, not what the storage sustains. [https://blog.glennklockwood.com/2021/10/iops-are-dumb.html](https://blog.glennklockwood.com/2021/10/iops-are-dumb.html)

## 2. The standard benchmark suite each vendor/community uses

### 2.1 Core tools

- **IOR** (LLNL, MPI-parallel): the reference parallel-filesystem bandwidth benchmark; supports file-per-process, single-shared-file, strided/reordered access, POSIX/MPI-IO APIs; used for HPC storage acceptance tests (e.g., ULHPC measured 23 GB/s read / 55 GB/s write on GPFS at acceptance). [https://www.vi4io.org/tools/benchmarks/ior](https://www.vi4io.org/tools/benchmarks/ior), [https://hpc-docs.uni.lu/filesystems/gpfs](https://hpc-docs.uni.lu/filesystems/gpfs)
- **mdtest** (bundled with IOR): MPI-parallel metadata benchmark; phases = tree creation, directory ops, file create/stat/read/rename/delete, tree removal; reports ops/s per phase. [https://www.vi4io.org/tools/benchmarks/mdtest](https://www.vi4io.org/tools/benchmarks/mdtest), [https://www.glennklockwood.com/garden/mdtest](https://www.glennklockwood.com/garden/mdtest)
- **fio**: the standard client-side load generator. Reference profiles: WEKA's bandwidth job (`bs=1Mi rw=read iodepth=1 numjobs=32`, libaio, `direct=1`, `group_reporting`, 30 s runtime) and IOPS job (`bs=4k rw=randread iodepth=8 numjobs=64`) [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access); Google Managed Lustre's high-scale distribution test uses `fio --server` mode on every client VM (2048 clients reading one 40 GiB file, avg 36.7 GB/s) [https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development](https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development); croit uses `fio --direct=1 --fsync=1 --rw=write --bs=4k --numjobs=N --iodepth=1` for raw-device baselining. [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
- **pfind**: IO500's parallel `find` for namespace traversal scoring. [https://io500.org/about](https://io500.org/about)
- **md-workbench**: IO500 *extended-mode* concurrent-metadata benchmark (the community's top-requested addition: 53% of surveyed users wanted concurrent metadata ops tested). [https://io500.org/files/ISC22_IO500_Presentation.pdf](https://io500.org/files/ISC22_IO500_Presentation.pdf)

### 2.2 IO500 — the community list methodology

- **Structure** (io500.org/about): ior-easy-write/read (file-per-process, max throughput), ior-hard-write/read (one shared file, interleaved 47008-byte records), mdtest-easy (zero-byte files, own directory per process), mdtest-hard (3901-byte files in one *shared* directory), find-easy (scan all created files for a pattern). Every read/stat/delete phase deliberately operates on files created by a process **on a different node**. Bandwidth score = geometric mean of GiB/s results; metadata score = geometric mean of kIOPS; overall = geometric mean of the two. [https://io500.org/about](https://io500.org/about), [https://software.llnl.gov/benchmarks/80_io500/io500.html](https://software.llnl.gov/benchmarks/80_io500/io500.html)
- **Hard rules that keep it honest** (io500.org/rules/submission): (2) read-after-write — freshly written data must be correctly readable *from a different client node* after close; (4) stonewall timer must be 300 s on all create/write phases; (5) output files may not be pre-created; (8) all data must reach persistent storage within the measured time (a caching layer must not ack early); (9) no dedup/compression/content-dependent reduction — results must be dataset-independent; (14) awards require ≥10 physical client nodes; there are dedicated **10-node lists** (exactly 10 physical clients, ≥1 process each; find may use fewer). [https://io500.org/rules/submission](https://io500.org/rules/submission)
- **Who's on it (vendor proof points):** DDN EXAScaler/Lustre repeatedly tops 10-node lists (SC23: AI400X2-I, 10 nodes/640 procs, score 483.74; ISC23 AI400X2-II 1,127.22) [https://io500.org/list/sc23/full](https://io500.org/list/sc23/full); IBM Spectrum Scale entries include U. Chicago Randi (SC23, 10 nodes, score 119.36) [https://io500.org/list/sc25/ten-production](https://io500.org/list/sc25/ten-production); WEKA's MSKCC IRIS run (261 nodes / 27,144 processes, score 1,753.69) sits in the production list top-10 [https://io500.org](https://io500.org); VAST entered via customer Janelia Research Campus (SC24, 32 nodes / 2,048 procs, score 118.59, production list) [https://io500.org](https://io500.org); Hammerspace + Samsung posted the first standards-based Linux/pNFS top-10 10-node Production result (SC25) [https://finance.yahoo.com/news/hammerspace-breaks-io500-barriers-first-204700204.html](https://finance.yahoo.com/news/hammerspace-breaks-io500-barriers-first-204700204.html); Argonne's Aurora (DAOS) holds #1 on the SC25 10-node production list (score 2,885.57) [https://io500.org/list/sc25/ten-production](https://io500.org/list/sc25/ten-production).
- **Known criticisms to keep in mind:** ior-hard's 47008-byte pattern "no real workload does" (favors log-structured FS like DAOS) and write-then-immediately-read misses real write→compute→read pipelines where systems like VAST repack/compress/GC between (Glenn Klockwood). [https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb](https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb); VAST's own position: customers submit IO500 as bragging; highly tunable systems get tuned for the run, and cross-vendor scores aren't normalized by system size/SSD count (Blocks & Files coverage). [https://www.blocksandfiles.com/ai-ml/2025/06/20/ddn-tops-io500-10-node-list-for-hpc-storage/1609176](https://www.blocksandfiles.com/ai-ml/2025/06/20/ddn-tops-io500-10-node-list-for-hpc-storage/1609176)

### 2.3 MLPerf Storage — the AI-workload suite

- Maintained by MLCommons; emulates accelerators (B200/MI355-class in v3.0) via DLIO — real PyTorch data path, sleep-based compute — and reports samples/s + MB/s **valid only while all simulated accelerators stay ≥90% utilized** (v3.0 rule; earlier versions 95%+). [https://mlcommons.org/benchmarks/storage](https://mlcommons.org/benchmarks/storage), [https://mlcommons.org/working-groups/benchmarks/storage](https://mlcommons.org/working-groups/benchmarks/storage)
- Workloads: 3D-UNet, ResNet-50, CosmoFlow training, checkpoint, and (v3.0) vector search / LLM inference caching. [https://mlcommons.org/benchmarks/storage](https://mlcommons.org/benchmarks/storage)
- WEKA submits and blogs results (GPU-utilization framing: "measures the number of virtual accelerators at close to maximum utilization"). [https://www.weka.io/article/fit-for-purpose-gpu-utilization](https://www.weka.io/article/fit-for-purpose-gpu-utilization), [https://www.weka.io/article/weka-sets-new-records-with-unofficial-mlperf-storage-v0-5-benchmark](https://www.weka.io/article/weka-sets-new-records-with-unofficial-mlperf-storage-v0-5-benchmark)
- Hammerspace published full MLPerf Storage v2.0 configs — clients mount `nfs -o vers=4.2,port=20492,nconnect=16`, server tuned with `RPCNFSDCOUNT=64` — and a comparison table vs DDN/HPE/WEKA (standard NFS client vs Lustre/WEKA proprietary clients). [https://hammerspace.com/hammerspace-mlperf-storage-v2-0-benchmark-results](https://hammerspace.com/hammerspace-mlperf-storage-v2-0-benchmark-results)

## 3. Cross-node behaviors a single-node test misses

1. **Write-on-A / read-on-B coherence.** IO500 bakes it into the rules (rule 2: freshly written data must read back correctly from a different client node after close) and into every phase design (each read/stat/delete targets files created by a process on another node). Single-node tests hit the local page cache instead. [https://io500.org/rules/submission](https://io500.org/rules/submission), [https://io500.org/about](https://io500.org/about)
2. **Aggregate contention on shared extents.** GPFS revokes/reissues the write token on overlapping byte ranges — nearly every write pays token management when nodes append to one file; non-overlapping ranges get true byte-range tokens (gpfsug list). Lustre's shared-file numbers (20–65% of file-per-process) are invisible to a single-node run. CephFS turns the same pattern into atomic RADOS-object updates, i.e., a latency benchmark. [https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html](https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html), [https://cug.org/proceedings/cug2017_proceedings/includes/files/pap141s2-file1.pdf](https://cug.org/proceedings/cug2017_proceedings/includes/files/pap141s2-file1.pdf), [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
3. **Metadata hot-directory contention.** Parent-directory locks serialize opens across nodes (INCD); CephFS MDS cache-pressure warnings only appear with many clients hammering one shared directory (croit). [https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices](https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices), [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
4. **Hot-file read storms.** Thousands of clients reading the *same* file (shared checkpoint/model weights) cause localized hotspotting that idles GPU clusters — Google's Managed Lustre work targets exactly this (67% improvement distributing one 40 GiB file to 2,048 clients, avg 36.7 GB/s). [https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development](https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development)
5. **Aggregate scaling & per-client ceilings.** CERN's CephFS eval: write throughput scales linearly with client count only until the cluster ceiling (6 of 8 clients saturate it), and one kernel client caps at ~6 GiB/s — a single-node test can never see either knee. [https://cds.cern.ch/record/2790637/files/document.pdf](https://cds.cern.ch/record/2790637/files/document.pdf)
6. **Client-count-dependent client-side behavior.** One cephfs mount per host shares a single flush kworker (croit); Lustre client lock LRU sizing is per-client but interacts with server callback volume (AWS FSx guidance). [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization), [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)
7. **Failure propagation.** A single node holding a critical GPFS token can hang the entire cluster; Lustre lock-waiting timeouts exist to keep ignored blocking callbacks from cascading into evictions. Single-node tests can't observe either. [https://www.spectrumscaleug.org/wp-content/uploads/2025/04/SSUG24NYC11-Storage-Scale-Network-Topics-NYC.pdf](https://www.spectrumscaleug.org/wp-content/uploads/2025/04/SSUG24NYC11-Storage-Scale-Network-Topics-NYC.pdf), [https://srcc.stanford.edu/sites/g/files/sbiybj25536/files/media/file/lustre_timeout_hierarchy.pdf](https://srcc.stanford.edu/sites/g/files/sbiybj25536/files/media/file/lustre_timeout_hierarchy.pdf)
8. **Fair-share under load.** Weakest coverage across all sources — IO500 has no fairness phase; the community's answer (md-workbench concurrent-ops, extended mode) is still opt-in. Note as an open gap; the closest evidence is workload-balance diagnostics (FSx OST-imbalance CloudWatch guidance). [https://io500.org/files/ISC22_IO500_Presentation.pdf](https://io500.org/files/ISC22_IO500_Presentation.pdf), [https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance-tips.html)

## 4. Tuning knobs that fake benchmarks

- **Client readahead cranked for the run:** DDN's own LUG IO500 slide documents `llite.*.max_read_ahead_mb=2048` and aggressive RPC settings (`max_pages_per_rpc=16M`, `max_rpcs_in_flight=16`) as *benchmark* tunings — readahead inflates sequential-read numbers that real mixed workloads won't see. [https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf](https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf)
- **Server-side caches disabled… or left on:** the same DDN slide disables OSS read/write caches (`read_cache_enable=0`, `writethrough_cache_enable=0`) for IO500, while the Mainz GPFS thesis notes HDD file-create benchmarks actually measure non-volatile controller cache, not disk. Both directions show cache state deciding the score. [https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf](https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf), [https://www.staff.uni-mainz.de/vef/pubs/vef2016thesis.pdf](https://www.staff.uni-mainz.de/vef/pubs/vef2016thesis.pdf)
- **Page cache / buffered I/O on the client.** IO500's own defense: a `drop-caches` hook (croit's `/usr/local/bin/drop_caches`: `echo 3 > /proc/sys/vm/drop_caches` on every client) and a design that reads only after writing everything, deliberately making caches ineffective; croit confirmed raising Ceph OSD memory target had *zero* effect for exactly this reason. [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
- **fio without `direct=1` silently loses queue depth:** on Linux, libaio is not async for buffered I/O, so `iodepth>1` isn't actually achieved — check the I/O depth distribution in fio output (fio docs). WEKA's and Google's published profiles all use `direct=1`. [https://fio.readthedocs.io/en/latest/fio_doc.html](https://fio.readthedocs.io/en/latest/fio_doc.html), [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access)
- **Early-ack caching layers.** IO500 rule 8 exists because a write-back cache can acknowledge closes before data is durable — a benchmark (and a production checkpoint) then "passes" on data that a power loss would destroy. [https://io500.org/rules/submission](https://io500.org/rules/submission)
- **Dedup / compression / zero-elimination.** IO500 rule 9 bans content-dependent reduction because the benchmark's partially predictable content would otherwise let appliances inflate scores; real systems (e.g., VAST) legitimately compress/GC *between* write and a much later read, so a naive write-then-read test mispredicts them in the opposite direction. [https://io500.org/rules/submission](https://io500.org/rules/submission), [https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb](https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb)
- **Short runs & warm repeats.** croit found sub-4-second phases (30 s stonewall) too short for reliable, reproducible numbers — hence the 300 s stonewall rule; repeated runs on an already-populated tree also hit client/server caches and allocator state. [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization), [https://io500.org/rules/submission](https://io500.org/rules/submission)
- **NFS transport options that change the physics:** `nconnect`, RDMA, multipath each multiply client bandwidth (VAST: 2 → 7 → 9 → 162 GB/s) — a certification that benchmarks the default mount is certifying a strawman. [https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1](https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1)
- **OS-level knobs that move scores legitimately but deceptively:** CPU `performance` governor took croit's RBD 4K-sync-write from 441 → 2,369 IOPS; disabling C6 helped "hard" latency-bound phases but hurt others; jumbo frames (MTU 9000) once corrupted the filesystem via MDS overload. These belong in the config record, not silently in a leaderboard run. [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
- **IO500 data-organization phase (rule 15) allows tuning the four phase directories** (e.g., `lfs setstripe`) — legitimate, but it means scores assume tuned layouts; a cert run should record the striping used. [https://io500.org/rules/submission](https://io500.org/rules/submission)

## 5. What a 2-hour rack certification should adopt — and skip

Context: a rack cert must catch the pathologies in §1 (MDS storms, lock thrash, coherence stalls, single-client ceilings, small-IO death) within ~120 minutes, on a fixed node count, with production settings — not chase a leaderboard score.

### Adopt (IO500/IOR/mdtest patterns, ~110 min of bench time)

1. **Cross-node read-after-write correctness gate (5 min).** IO500 rule 2 as a *test*, not just a rule: node A writes + closes; node B reads and verifies checksums. Catches eager-coherence stalls and unsafe client caching cheaply. [https://io500.org/rules/submission](https://io500.org/rules/submission)
2. **ior-easy pattern: file-per-process 1 MiB streaming write then read (2×8 min, 2 node counts).** Run at e.g. 8 nodes then all rack nodes; reads must target files written by *other* nodes (IO500 phase design). Reports aggregate GiB/s and per-node scaling knee. Use `-k` fresh files per run or unique dirs; record striping (rule 15 analog). [https://io500.org/about](https://io500.org/about), [https://software.llnl.gov/benchmarks/80_io500/io500.html](https://software.llnl.gov/benchmarks/80_io500/io500.html)
3. **ior-hard pattern: single-shared-file, 47008-byte strided writes + reads (2×8 min).** This is the lock/token-thrash detector: GPFS write-token ping-pong, Lustre LDLM extent-lock handoff, CephFS atomic RADOS updates all light up here (hard ≈ 3% of easy bandwidth on croit's cluster is a normal-looking ratio, not a bug). [https://io500.org/about](https://io500.org/about), [https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html](https://tigershark.gpfsug.org/pipermail/gpfsug-discuss/2019-November/006672.html), [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
4. **mdtest-easy pattern: create/stat/read/delete, zero-byte files, per-process dirs, cross-node stat (4×6 min).** Stat on files created by another node is the coherence-preserving metadata number; watch MDS/MDS-rank CPU and client "cache pressure" warnings during it (the croit collapse signature). [https://io500.org/about](https://io500.org/about), [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
5. **mdtest-hard pattern: 3901-byte files in ONE shared directory (write + delete, 2×6 min).** The shared-directory MDS-storm stressor — this is the pattern that takes real filesystems offline (INCD). Cap it: 300 s stonewall equivalent or a fixed file count; abort criteria on MDS health warnings. [https://io500.org/about](https://io500.org/about), [https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices](https://wiki.incd.pt/books/filesystem-user-guide/page/lustre-best-practices)
6. **fio 4K random-read profile, single client and full rack (2×5 min).** WEKA's exact job shape (libaio, `direct=1`, `iodepth=8`, `bs=4k randread`, `group_reporting`) plus an fio-server fan-out across all nodes; single-client run exposes the TCP/protocol ceiling, full-rack run exposes aggregate IOPS. Also do one 1 MiB sequential single-client run to measure the per-client bandwidth cap (VAST ~2 GB/s default-TCP class of result). [https://www.weka.io/article/fit-for-purpose-part-two-client-access](https://www.weka.io/article/fit-for-purpose-part-two-client-access), [https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development](https://cloud.google.com/blog/topics/developers-practitioners/democratizing-managed-lustre-with-lower-cost-and-frictionless-development), [https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1](https://kb.vastdata.com/documentation/docs/nfs-features-for-enhanced-performance-1)
7. **pfind over the created tree (5 min).** Cheap namespace-traversal sanity plus it exercises readdir at depth after mdtest. [https://io500.org/about](https://io500.org/about)
8. **Cache hygiene throughout:** `echo 3 > /proc/sys/vm/drop_caches` on all clients between phases (IO500's own drop-caches hook), unique output dirs per phase, `direct=1` on fio, and verify libaio actually reaches the set iodepth (fio output distribution). [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization), [https://fio.readthedocs.io/en/latest/fio_doc.html](https://fio.readthedocs.io/en/latest/fio_doc.html)
9. **Report geometric-mean-style, per-phase numbers with a fixed config record** (striping, mount options incl. nconnect/RDMA, governor, pagepool/lru settings, versions). The IO500 scoring habit (geometric mean of BW and MD scores) prevents cherry-picking a single hero number. [https://www.glennklockwood.com/garden/io500](https://www.glennklockwood.com/garden/io500), [https://io500.org/about](https://io500.org/about)

### Skip (with reasons)

1. **A full official IO500 run.** Five 300-s stonewalled write phases + reads + find + cleanup realistically exceeds the whole 2-hour window by itself once you include the 300 s minimum per create/write phase and mdtest phases (croit's full run: individual phases run 300–950 s each; mdtest-easy-stat alone hit 5,694 s when MDS choked). Certify with the *patterns* above, not the scored submission. [https://io500.org/rules/submission](https://io500.org/rules/submission), [https://www.croit.io/blog/ceph-performance-benchmark-and-optimization](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)
2. **MLPerf Storage / DLIO.** Needs simulated-accelerator harness and model-specific I/O patterns; a rack cert needs POSIX-level signals, and MLPerf's own reviewers note its patterns aren't what real training does (tokens get bundled to whatever chunk size is fastest; prefetch moves reads to local SSD). [https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb](https://www.glennklockwood.com/garden/storage-benchmarking-is-dumb), [https://mlcommons.org/benchmarks/storage](https://mlcommons.org/benchmarks/storage)
3. **mdtest-hard full read phase (reads all 3901-B files back, cross-node).** Long, and mostly re-measures the same MDS+coherency path as hard-write/hard-stat; sample it or skip. [https://io500.org/about](https://io500.org/about)
4. **Benchmark-only server cache disables and readahead cranks** (`read_cache_enable=0`, `writethrough_cache_enable=0`, `max_read_ahead_mb=2048`, etc.). Those are leaderboard tunings; a cert must measure the configuration the rack will run in production. Record deltas if you test them, but don't certify on them. [https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf](https://wiki.lustre.org/images/9/92/LUG2019-IO500_Storage_Benchmark_for_HPC-Dilger.pdf)
5. **Multiple statistical repeats.** IO500 scores are single-run submissions with community reproducibility scores; in 2 hours, one clean run per pattern with config-recorded variance beats three runs of half the patterns. Keep 10–15 min reserve for one re-run of whatever phase looked anomalous. [https://io500.org/rules/submission](https://io500.org/rules/submission)
6. **Un-normalized cross-vendor score comparisons.** If the cert result gets compared to an IO500 list entry, normalize per client node and note the submission's node count/process count (10-node lists vs full production list) — VAST's critique (scores not normalized by SSD count/system size) applies to internal comparisons too. [https://www.blocksandfiles.com/ai-ml/2025/06/20/ddn-tops-io500-10-node-list-for-hpc-storage/1609176](https://www.blocksandfiles.com/ai-ml/2025/06/20/ddn-tops-io500-10-node-list-for-hpc-storage/1609176), [https://io500.org/rules/submission](https://io500.org/rules/submission)

### Suggested 120-minute run sheet

| Min | Phase | Pass signal |
|---|---|---|
| 0–10 | Setup, config capture, drop caches, cross-node write/read-verify | Verified checksums on B |
| 10–26 | ior-easy FPP write+read @ 8 nodes, then @ all nodes | ~linear per-node scaling; no cliff |
| 26–42 | ior-hard SSF 47008B write+read @ all nodes | Accept hard/easy ratio; no 100× collapse beyond expected |
| 42–66 | mdtest-easy W/S/R/D, cross-node stat | Stable kIOPS; MDS CPU < 100%, no cache-pressure warnings |
| 66–78 | mdtest-hard shared-dir W+D | No MDS health warnings; no runaway latency |
| 78–88 | fio 4K randread single-client + rack-wide | Per-client ceiling known (≈NIC/TCP class), aggregate scales |
| 88–93 | pfind over created tree | Completes; kIOPS recorded |
| 93–105 | Buffer: re-run anomalous phase | Reproducible within ~10% |
| 105–120 | Teardown, delete test tree (measured — it's also a benchmark), report | Geometric-mean summary + config record |
