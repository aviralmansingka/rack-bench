# AI Labs: How Large GPU Fleets Actually Use Storage — and What Breaks

Research brief, compiled October 2026. Question: how do frontier-scale GPU fleets actually use storage, what storage-caused failures are documented, and what would a training tenant demand be certified for before accepting a cluster?

Method: primary sources only for claims (Meta engineering posts + the Llama 3 paper, NVIDIA DGX SuperPOD reference architectures and developer blog, DeepSeek's Fire-Flyer paper and 3FS, xAI's Colossus page + the ServeTheHome/Supermicro walkthrough, Microsoft Azure posts covering OpenAI's training storage, OPT-175B logbook, MosaicML/Databricks, Imbue via Latent Space, SemiAnalysis). Every claim carries its URL inline. Secondary/anecdotal items are flagged as such. OpenAI publishes no first-party storage detail for its current fleet; its storage story is covered via Microsoft Azure, which builds and operates OpenAI's training infrastructure.

## 1. Checkpoint I/O pattern: synchronized, bursty, pause-critical writes

### 1.1 What a checkpoint contains and how big it is

A full training checkpoint is model weights + optimizer states + gradients (+ RNG, scaler, and dataloader state), and the optimizer dominates: for a 70B model with AdamW, 130 GB of BF16 weights, 521 GB of FP32 optimizer moments, and 130 GB of gradients make a 782 GB checkpoint — the optimizer state alone is 4x the weights — and 405B/DeepSeek-V3-class checkpoints reach 4.5 TB / 7.5 TB ([NVIDIA nvCOMP blog](https://developer.nvidia.com/blog/cut-checkpoint-costs-with-about-30-lines-of-python-and-nvidia-nvcomp/)). At Meta, checkpointing is described as saving "each GPU's model state, ranging from 1 MB to 4 GB per GPU, for recovery and debugging" — i.e., thousands of per-rank files written in one synchronized event ([Llama 3 paper §3.3.1](https://arxiv.org/html/2407.21783v3)). DeepSeek's checkpoint manager chunks parameters and optimizer states and records per-tensor index/offset so loading is targeted, not a bulk read ([Fire-Flyer paper §VII-A](https://arxiv.org/html/2408.14158)).

### 1.2 Frequency

- NVIDIA calls checkpointing every 15–30 minutes "standard practice for fault tolerance… load-bearing infrastructure, not optional overhead" at 1000+ GPU scale ([nvCOMP blog](https://developer.nvidia.com/blog/cut-checkpoint-costs-with-about-30-lines-of-python-and-nvidia-nvcomp/)).
- DeepSeek checkpoints asynchronously every ~5 minutes, so a hardware failure costs at most 5 minutes of progress ([Fire-Flyer paper §VII-A](https://arxiv.org/html/2408.14158)).
- Microsoft's Azure AI infrastructure guidance says to checkpoint model state "at regular intervals such as every 500 iterations" and store it in the parallel file system tier ([Azure CAF storage recommendations](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai/infrastructure/storage)).
- Meta's SDC-triage playbook ("hyper-checkpointing") deliberately raises checkpoint frequency to ever-higher rates to bisect which node is corrupting training ([Meta AI hardware reliability post](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/)).
- Meta explicitly states the design goal is to "increase checkpoint frequency to reduce the amount of lost work after a recovery" ([Llama 3 paper §3.3.1](https://arxiv.org/html/2407.21783v3)).
- SemiAnalysis notes the common production pattern of saving only once per ~100 iterations and quantifies the loss: on a 100k-GPU cluster with 2-second iterations, a failure at iteration 99 wastes up to 229 GPU-days of work ([100,000 H100 Clusters](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network)).

### 1.3 Burst rate — the number clusters are actually built around

- **Meta (Llama 3 405B, 16,384 H100s):** the Tectonic-backed storage fabric is 240 PB across 7,500 SSD servers, sustaining 2 TB/s with 7 TB/s peak, and "a major challenge is supporting the highly bursty checkpoint writes that saturate the storage fabric for short durations" ([Llama 3 paper §3.3.1](https://arxiv.org/html/2407.21783v3)). The same fabric is exposed to the cluster via a FUSE filesystem over a Flash-optimized Tectonic, which "enables thousands of GPUs to save and load checkpoints in a synchronized fashion (a challenge for any storage system)" — Meta's own link on that phrase points at the thundering-herd problem ([Building Meta's GenAI Infrastructure](https://engineering.fb.com/2024/03/12/data-center-engineering/building-metas-genai-infrastructure/)). With the new stack, Meta optimized "checkpointing across thousands of ranks to run in hundreds of milliseconds" (staged/async commit) ([same post](https://engineering.fb.com/2024/03/12/data-center-engineering/building-metas-genai-infrastructure/)).
- **DeepSeek (Fire-Flyer 2, 10,000 A100s):** checkpoint chunks go to 3FS via a batch-write API at >10 GiB/s per node, so a full periodic save completes "in just a few seconds" and restores equally fast via batch read ([Fire-Flyer paper §VII-A](https://arxiv.org/html/2408.14158)). The 3FS storage plane behind it: 180 storage nodes × 16 NVMe SSDs + 2×200 Gbps IB per node = 360×200 Gbps (~9 TB/s outbound), 8 TB/s actually achieved in aggregate read, >20 PiB raw with mirroring ([Fire-Flyer §VI-B](https://arxiv.org/html/2408.14158)); the open-source stress test shows 6.6 TiB/s aggregate read on 180 storage nodes and 500+ clients with background training traffic ([3FS GitHub](https://github.com/deepseek-ai/3fs)).
- **NVIDIA DGX SuperPOD reference architecture (the de facto vendor spec):** checkpoint files "can be terabytes in size and while not written frequently are typically written synchronously that blocks forward progress of DL models"; for LLM/large-model use cases "consider at least ½ of the read performance as recommended write performance"; and the RA tables specify tiered aggregate minimums — for DGX B200: single-SU aggregate read 40 GBps (standard) to 125 GBps (enhanced), single-SU write 20–62 GBps, 4-SU aggregate read 160–500 GBps, 4-SU write 80–250 GBps ([DGX SuperPOD B200 storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/storage-architecture.html)). The H100 version's tables run single-node read 4–40 GBps and write 2–20 GBps by tier, single-SU aggregate read 15–125 GBps and write 7–62 GBps, 4-SU aggregate read 60–500 GBps and write 30–250 GBps, with the note that single-node reads should ideally approach the 80 GBps network maximum ([DGX SuperPOD H100 storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html)).
- **Microsoft/Azure (OpenAI's training substrate):** Azure Blob Storage was evolved to "exabytes of capacity, 10s of Tbps throughput, and millions of IOPS to GPUs," a single storage account demonstrated >50 Tbps read, and "Azure Blob Storage is also the foundation that enables OpenAI to train and serve models at unprecedented speed and scale" ([Azure Storage innovations](https://azure.microsoft.com/en-us/blog/azure-storage-innovations-unlocking-the-future-of-data/)); OpenAI's own customer story says storage requirements "especially on throughput scale and reliability" drove it onto Azure Blob scaled accounts ([OpenAI + Azure Blob customer story](https://www.microsoft.com/en/customers/story/23427-openai-lp-azure-blob-storage/)). Azure Managed Lustre scales to 512 GBps per filesystem for the hot tier ([Azure Storage blog](https://azure.microsoft.com/en-us/blog/azure-storage-innovations-unlocking-the-future-of-data/)).
- **xAI Colossus:** >0.5 EB of total storage "for training data and checkpoints" behind 200,000 H100s ([x.ai/colossus](https://x.ai/colossus)); the ServeTheHome/Supermicro walkthrough shows a dedicated fleet of 1U NVMe storage nodes (storage software from multiple vendors, nearly all servers Supermicro), and notes large AI clusters are moving from disk to flash because at this scale flash wins TCO via power and density ([Supermicro/STH Colossus case study PDF](https://www.supermicro.com/CaseStudies/Success_Story_xAI_Colossus_Cluster.pdf)); the accompanying video states storage is delivered over the network to a "giant storage cluster" because training needs more storage than fits in GPU servers and every server needs access to all of it ([STH video](https://youtu.be/Jf8EPSBZU7Y)).

### 1.4 Synchronicity and what happens to the training loop

- NVIDIA's storage-architecture guidance states checkpoints "are typically written synchronously that blocks forward progress of DL models" and, for NLP/LLM, "peak performance for reads and writes are needed for creating and reading checkpoint files. This is a synchronous operation and training stops during this phase" ([DGX SuperPOD storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html)).
- In the synchronous baseline, "all 8 GPUs sit completely idle… the training loop blocks until the last byte hits storage": 782 GB at 5 GB/s (typical Lustre/GPFS over IB) = 156 s of GPU wait per checkpoint, 62.6 h/month, $2,203/month on 8 GPUs at $4.40/GPU-h; >$200,000/month idle cost at 128 GPUs training a 405B model; and 1.13 PB/month written for a 70B model at 30-minute cadence ([nvCOMP blog](https://developer.nvidia.com/blog/cut-checkpoint-costs-with-about-30-lines-of-python-and-nvidia-nvcomp/)).
- The async/staged alternative: DeepSeek moves state GPU→CPU asynchronously and writes to 3FS in seconds without impacting training ([Fire-Flyer §VII-A](https://arxiv.org/html/2408.14158)); Meta commits across thousands of ranks "in hundreds of milliseconds" ([GenAI infra post](https://engineering.fb.com/2024/03/12/data-center-engineering/building-metas-genai-infrastructure/)); Meta's storage team lists "supporting checkpointing without stalling GPUs at even higher scale" as ongoing future work ([AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
- Storage-side burst handling is a real subsystem, not a given: at Meta, "during checkpoint events, it is common for the client to create sharp egress spikes. This in turn can cause congestion, timeouts, and retries, eventually stalling GPUs," which required dynamic concurrency control in the client SDK ([Meta AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
- Second-order effect Meta documents: when tens of thousands of GPUs all pause at once "waiting for checkpointing or collective communications to finish," datacenter power swings by tens of megawatts in an instant — checkpoint cadence is a grid-stability parameter ([Llama 3 paper §3.3.4](https://arxiv.org/html/2407.21783v3)); xAI similarly deployed Tesla Megapacks to buffer millisecond-scale power spikes from the training workload ([Supermicro/STH PDF](https://www.supermicro.com/CaseStudies/Success_Story_xAI_Colossus_Cluster.pdf)).

### 1.5 Durability / fsync / atomicity requirements

- DeepSeek's 3FS provides strong consistency via Chain Replication with Apportioned Queries (CRAQ) for writes and transactional metadata (FoundationDB), i.e., a checkpoint write is either consistent or fails detectably ([3FS GitHub](https://github.com/deepseek-ai/3fs), [Fire-Flyer §VI-B](https://arxiv.org/html/2408.14158)).
- Meta requires "thousands of GPUs to save and load checkpoints in a synchronized fashion" over a strongly consistent erasure-coded fabric (Tectonic) ([GenAI infra post](https://engineering.fb.com/2024/03/12/data-center-engineering/building-metas-genai-infrastructure/), [Tectonic FAST '21 paper](https://www.usenix.org/conference/fast21/presentation/pan)).
- A 2026 analysis of AI infrastructure failures states "non-atomic checkpointing consumes 12–43% of training time" and "remote storage checkpoints take 30–40 minutes every three hours," and puts hourly checkpointing on a 512-GPU cluster above $4,000/day — i.e., atomic, crash-consistent checkpoint commit is treated as a structural requirement, not a nicety ([arXiv 2603.03736, secondary analysis](https://arxiv.org/pdf/2603.03736)).
- Inference-side durability is the same story at DeepSeek: 3FS-KV persists KV-cache to disk with read-write separation and GC delete IOPS as a first-class measured workload ([3FS GitHub](https://github.com/deepseek-ai/3fs)).
- Gap (flagged honestly): no public lab post spells out the syscall-level contract (per-file fsync/fdatasync, atomic rename/manifest commit, O_DSYNC semantics). It is inferable — every published architecture stages then atomically commits a manifest of per-rank files — but the exact durability contract is unpublished.

### 1.6 What a failed or slow checkpoint costs

- Idle-GPU cost of slow synchronous writes: $2,203/month (8 GPUs, 70B) to >$200,000/month (128 GPUs, 405B) in GPU wait time alone, before storage fees ([nvCOMP blog](https://developer.nvidia.com/blog/cut-checkpoint-costs-with-about-30-lines-of-python-and-nvidia-nvcomp/)).
- Lost work on failure: up to 229 GPU-days on a 100k-GPU cluster when a 100-iteration checkpoint interval is interrupted near its end ([SemiAnalysis 100k H100 clusters](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network)).
- Llama 3 405B: 466 interruptions over 54 days still yielded >90% effective training time, achieved by "reduced job startup and checkpointing time" and fast diagnosis tooling ([Llama 3 paper §3.3.4](https://arxiv.org/html/2407.21783v3)); the earlier Llama 3 (8B/70B) program credits "new scalable storage systems that reduce overheads of checkpointing and rollback" for >95% effective training time ([Meta Llama 3 blog](https://ai.meta.com/blog/meta-llama-3)).
- The worst case is a checkpoint you cannot trust: with a silent-data-corrupting node, "restarts from checkpoints will eventually fail" until the offending node is identified and quarantined — Meta's response is hyper-checkpointing plus deterministic replay for triage ([Meta AI hardware reliability](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/)).
- Historical baseline: OPT-175B (2021–22) suffered ~90 restarts over the run lineage and "at least 35 manual restarts and the cycling of over 100 hosts," resuming from the last saved checkpoint each time ([OPT paper](https://arxiv.org/pdf/2205.01068), [final logbook update](https://github.com/facebookresearch/metaseq/blob/main/projects/OPT/chronicles/final_update.md)); MosaicML cites the OPT logbook for "wasting thousands of GPU-hours replaying their data loading after crashes in order to resume training where they left off" ([MosaicML StreamingDataset blog](https://www.databricks.com/blog/mosaicml-streamingdataset)).

## 2. Dataset streaming pattern: shards, random reads, cache tiers

### 2.1 Shard-first layout

- MosaicML's StreamingDataset (used for Stable Diffusion on LAION-400m and GPT pretraining at scale) converts datasets to MDS shards in object storage (S3/GCS/OCI), has each machine download **disjoint** subsets so "no matter how many machines you train on, you only download the data once," and guarantees deterministic sample ordering independent of device count — which is what makes crash-resume exact instead of a replay ([MosaicML StreamingDataset blog](https://www.databricks.com/blog/mosaicml-streamingdataset), [streaming docs](https://docs.mosaicml.com/projects/streaming/en/stable/getting_started/main_concepts.html)).
- Sharding is the general answer to per-shard throttling: PyTorch's S3 IO guidance notes "each node in the cluster can generate a large number of data loading requests that hit a specific S3 shard. To avoid throttle, we recommend sharding training data across S3 buckets and S3 folders" ([PyTorch blog](https://pytorch.org/blog/announcing-cpp)); AWS's dataloading best-practices post adds the caveat that shards only help if access within a shard is sequential — Parquet/HDF5-style random access inside shards forfeits the sequential-read benefit ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/applying-data-loading-best-practices-for-ml-training-with-amazon-s3-clients/)).
- DeepSeek's answer is stronger storage instead of access-pattern discipline: 3FS "eliminates the need for prefetching or shuffling datasets by enabling random access to training samples across compute nodes," with data-prep pipelines (smallpond) writing intermediate outputs into the same filesystem ([3FS GitHub](https://github.com/deepseek-ai/3fs)).

### 2.2 Random reads are the real training-read workload

- NVIDIA's reference architecture: "The key I/O operation in DL training is re-read… it must be reused again and again due to the iterative nature of DL training"; high-speed storage "must be optimized for small, random I/O patterns… most DL workloads will be read-dominant"; for >30 TB image/video datasets, 4 GBps per GPU of read performance is needed ([DGX SuperPOD H100 storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html)).
- For un-sharded small-file datasets the regime is latency-bound, not bandwidth-bound: each object GET pays a time-to-first-byte that dominates transfer time; a public benchmark saturates at ~134 samples/sec/GPU on random-access small images (within 3% of AWS S3's own reported figure) ([Tigris training benchmark](https://www.tigrisdata.com/blog/training-object-storage/)).
- Meta frames the requirement as bounded tail latency: dataloaders prefetch the next batch while the GPU computes the current one, and "if one GPU is slow, this step will slow down all GPUs as well as the entire training" — hence the demand for "predictable and bounded latencies all the way up to pMax," hedged reads against "laggards" (slow storage nodes causing tail latency), and a distributed data cache serving an **80% average hit rate** with 1–2 ms metadata access from the read-plan cache ([Meta AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
- Storage traffic must not perturb training collectives: DeepSeek runs storage and computation traffic on one integrated fat-tree and had to enforce InfiniBand Service Level/Virtual Lane isolation between HFReduce, NCCL, 3FS, and other traffic, disable DCQCN (no parameter set served both traffic classes), use static routing, and add request-to-send flow control in 3FS to survive client-side incast at peak load ([Fire-Flyer §VI-A/VI-B](https://arxiv.org/html/2408.14158)); SemiAnalysis makes the same point for frontend-network designs — "irregular storage network traffic… would cause your entire all-reduces to slow down and not be predictively modeled," and multimodal video loading will make frontend bandwidth "fight between loading large video files and doing all reductions" ([100,000 H100 clusters](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network)).

### 2.3 Cache tiers (the universal architecture)

- Meta's current blueprint is an OS-style tiered cache: GPU-host memory as L1, GPU-host flash as L2, regional flash-backed BLOB storage as L3, with the global HDD-backed BLOB fabric as source of truth; dataloaders prefetch, an explicit `prefetch()` API hydrates L3 and pre-warms metadata, and TTL/LRU eviction holds L3 data across epochs for reuse ([Meta AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)). Historically, Meta trained Llama "directly over the Tectonic block layer by exposing an NFS-like FileSystem interface on top of it" and is migrating the training stack onto the BLOB (object) interface ([same post](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/), [@Scale talk: Training Llama — A Storage Perspective](https://atscaleconference.com/videos/training-llama-a-storage-perspective/)); Tectonic itself is an exabyte-scale, erasure-coded, flash/HDD-tiered block fabric ([Tectonic FAST '21](https://www.usenix.org/conference/fast21/presentation/pan), [Meta data-ingestion post](https://engineering.fb.com/2022/09/19/ml-applications/data-ingestion-machine-learning-training-meta/)).
- MosaicML: shards cached to local disk after epoch 1, async download so "training begins as soon as a batch's worth of samples are downloaded," 2-minute startup for Stable Diffusion over LAION-400m streaming from S3 on 128 A100s, and cache-limit eviction of LRU shards ([MosaicML StreamingDataset blog](https://www.databricks.com/blog/mosaicml-streamingdataset), [streaming GitHub](https://github.com/mosaicml/streaming)).
- Azure's published AI storage pattern is the same three tiers: a parallel filesystem (Azure Managed Lustre / NetApp Files / job-local NVMe via BeeGFS-on-demand) for hot data and checkpoints, Blob for inactive/long-term with lifecycle tiering, and Lustre↔Blob HSM sync for consistency ([Azure CAF storage recommendations](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai/infrastructure/storage), [Azure Storage blog](https://azure.microsoft.com/en-us/blog/azure-storage-innovations-unlocking-the-future-of-data/)).
- NVIDIA likewise specifies RAM as the first cache layer and local NVMe for staging/caching datasets that no longer fit in cache ([DGX SuperPOD storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html)); GPUDirect Storage is the mechanism to move data from remote filesystem or local NVMe directly into GPU memory at >40 GBps per node ([GPUDirect Storage page](https://developer.nvidia.com/gpudirect-storage), [Magnum IO architecture](https://developer.nvidia.com/blog/accelerating-io-in-the-modern-data-center-magnum-io-architecture/)).
- Egress economics drive the tiering: downloading ImageNet from S3 once costs ~$3 in egress, but four machines each pulling the full dataset costs $12 — redundant full-dataset downloads are the failure mode shard-disjoint caching eliminates ([MosaicML StreamingDataset blog](https://www.databricks.com/blog/mosaicml-streamingdataset)).

### 2.4 Ingestion and locality pain

- Meta: a training-job submission used to require a regional data-ingestion snapshot step that "depending on the dataset size, can take hours," which is why the tiered-cache "ingest once, read anywhere" redesign shipped ([AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
- Databricks' chief AI scientist (podcast, anecdotal): "I've certainly encountered issues where the literal data center where my GPUs were did not have enough object store to fit the datasets… you have to keep your data in a different region because the region is just out of storage" ([Latent Space: Training >70B LLMs on 10,000 H100 clusters](https://www.latent.space/p/llm-training-2024)); Imbue likewise built a deliberately simple local S3-like mirror because cluster internet egress was the bottleneck ([same interview](https://www.latent.space/p/llm-training-2024), [Imbue infrastructure post](https://imbue.com/research/70b-infrastructure/)).

## 3. Documented storage-caused training incidents

1. **Checkpoint bursts saturating the fabric (Meta, Llama 3 405B).** The storage fabric's defining challenge was "highly bursty checkpoint writes that saturate the storage fabric for short durations" ([Llama 3 paper §3.3.1](https://arxiv.org/html/2407.21783v3)). The same run's 54-day interruption table records 3 SSD host failures and 2 IO-expansion-board failures among the 419 unexpected interruptions, alongside 35 network switch/cable events and 7 NCCL-watchdog timeouts ([paper §3.3.4, Table 5](https://arxiv.org/html/2407.21783v3)).
2. **Checkpoint egress spikes stalling GPUs (Meta, blob-storage stack).** "During checkpoint events, it is common for the client to create sharp egress spikes. This in turn can cause congestion, timeouts, and retries, eventually stalling GPUs" — fixed with dynamic client-side concurrency control ([Meta AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
3. **Metadata latency as a showstopper (Meta).** The legacy blob stack's multi-layer metadata lookups "can cross regions, and it's not uncommon for latencies to add up to hundreds of milliseconds; one slow response from any of the lookups was sufficient" — fine for HDD-era workloads, "showstoppers for AI workloads with millisecond access to data in flash"; also "metadata hot shards" on frequently accessed blobs, and GPU-restart storms creating sharp traffic spikes on hot model weights ([Meta AI Storage Blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/)).
4. **Dataloader replay after crashes (Meta, OPT-175B).** Thousands of GPU-hours wasted re-iterating the dataloader to resume where the run left off after crashes — the incident MosaicML built StreamingDataset to prevent, quoting the OPT logbook ([MosaicML blog](https://www.databricks.com/blog/mosaicml-streamingdataset), [OPT-175B logbook](https://github.com/facebookresearch/metaseq/blob/main/projects/OPT/chronicles/OPT175B_Logbook.pdf), [OPT paper: ≥35 manual restarts, >100 hosts cycled](https://arxiv.org/pdf/2205.01068)).
5. **Cluster deleted by the cloud provider; buffer nodes fail checks (Meta, OPT-175B).** While replenishing a 12-node buffer pool (kept because ~2 machines/day fail), provider support "accidentally deleted our entire cluster" on Dec 21, 2021; it came back with 16 machines failing infrastructure checks ([OPT final logbook update](https://github.com/facebookresearch/metaseq/blob/main/projects/OPT/chronicles/final_update.md)).
6. **Untrusted checkpoints under silent data corruption (Meta, Llama 3).** SDC caused 6 of the 419 unexpected interruptions directly, and NaN propagation from a single bad accelerator can halt the cluster with restarts-from-checkpoint that "eventually fail" until the bad node is quarantined — checkpoint integrity and failure attribution are coupled problems ([Llama 3 paper Table 5](https://arxiv.org/html/2407.21783v3), [Meta AI hardware reliability](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/)). DeepSeek reports the same class: "computational errors and GPU memory errors not detected by ECC… led to models' gradnorm spikes, loss explosions and even non-convergence" ([Fire-Flyer §VII-C](https://arxiv.org/html/2408.14158)).
7. **Storage/allreduce interference on a shared fabric (DeepSeek).** One integrated network carrying HFReduce, NCCL, 3FS, and management traffic produced head-of-line blocking, incast congestion at peak storage load, and no workable congestion-control setting — resolved with SL/VL isolation, static routing, and 3FS request-to-send flow control ([Fire-Flyer §VI-A/VI-B](https://arxiv.org/html/2408.14158)). SemiAnalysis generalizes it: irregular storage traffic on the frontend network makes all-reduces unpredictable (straggler amplification) ([100k H100 clusters](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network)).
8. **Region/dataset capacity mismatches (Databricks/Imbue, anecdotal).** Datasets larger than a region's object-store capacity force cross-region data placement and slow iteration ([Latent Space interview](https://www.latent.space/p/llm-training-2024)).
9. **Checkpoint pauses as a power event (Meta).** All GPUs pausing for checkpointing at once swings datacenter power by tens of megawatts, "stretching the limits of the power grid" ([Llama 3 paper §3.3.4](https://arxiv.org/html/2407.21783v3)); xAI buffers the analogous millisecond spikes with Tesla Megapacks ([Supermicro/STH PDF](https://www.supermicro.com/CaseStudies/Success_Story_xAI_Colossus_Cluster.pdf)).
10. **The counterfactual: DeepSeek-V3 ran clean.** 2.788M H800 GPU-hours, 14.8T tokens, "we did not experience any irrecoverable loss spikes or perform any rollbacks" — on the 3FS/Fire-Fayer-style stack with 5-minute async checkpointing ([DeepSeek-V3 technical report](https://arxiv.org/html/2412.19437v1), [Fire-Flyer §VII-A](https://arxiv.org/html/2408.14158)). The report itself is silent on storage internals (see Gaps).

## 4. What infra teams measure before accepting a cluster

No lab publishes a complete acceptance-test list, but four public programs/documents define what gets measured:

1. **NVIDIA DGX SuperPOD reference architecture (vendor acceptance targets).** Tiered per-node and per-SU aggregate read/write GBps minimums (B200: 40–500 GBps read and 20–250 GBps write depending on SU count and tier; write ≥ ½ read for LLM checkpoints), single-node reads approaching the 80 GBps network max, GDS-enabled apps reading >40 GBps directly into GPUs, and 4 GBps per GPU for >30 TB vision datasets — with the explicit instruction to "characterize workloads… before finalizing performance and capacity requirements" ([DGX SuperPOD B200 storage architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/storage-architecture.html), [H100 version](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html)).
2. **NVIDIA certification programs (formal storage acceptance).** NVIDIA-Certified Storage (announced GTC 2025) plus DGX BasePOD/SuperPOD Storage Certification and NCP Storage Certification — each includes "performance testing as well as validation that partner storage systems adhere to design best practices" for AI workloads ([NVIDIA blog](https://blogs.nvidia.com/blog/nvidia-certified-enterprise-storage/)); the north-south networking post ties it together: "every time an AI model checkpoints its progress mid-training, it moves massive amounts of data across north-south pathways to persistent storage… These checkpoint files, which can span several terabytes" ([NVIDIA technical blog](https://developer.nvidia.com/blog/north-south-networks-the-key-to-faster-enterprise-ai-workloads/)).
3. **DeepSeek's weekly node validator (a published per-node acceptance suite).** Runs weekly on every node before it is allowed into the scheduler: CPU stress + memory bandwidth, byte-by-byte GPU memory test, GEMM with full memory occupancy, intra-node allreduce/NVLink bandwidth, and — directly on point — a "storage bandwidth stress test to make sure storage is functioning normally" ([Fire-Flyer §VII-B](https://arxiv.org/html/2408.14158)).
4. **Meta's cluster bring-up and rating systems.** Meta's reliability program explicitly optimizes "fault categorization, device triage, node selection, cluster validation, and checkpoint restore" ([Meta AI hardware reliability](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/)), uses PyTorch's NCCL flight recorder to diagnose hangs at scale ([Llama 3 paper §3.3.4](https://arxiv.org/html/2407.21783v3)), and treats effective training time (>90–95%) as the outcome metric that storage/checkpoint overhead must clear ([Llama 3 paper](https://arxiv.org/html/2407.21783v3), [Llama 3 blog](https://ai.meta.com/blog/meta-llama-3)); Meta states the programs that mattered: "If jobs fail too frequently, we stop making progress because of how long it takes to checkpoint and restart jobs," and industry collaboration drove interruption rates down ~50x ([Meta's Infrastructure Evolution](https://engineering.fb.com/2025/09/29/data-infrastructure/metas-infrastructure-evolution-and-the-advent-of-ai/)).
5. **Third-party/independent checklists.** Imbue open-sourced its cluster-health scripts (NIC/GPU/dmesg/boot-line health checks; goal: verify all 4,096 GPUs before trusting MFU numbers) and cites a ~3%-of-machines-per-week industry failure rule of thumb ([Latent Space interview](https://www.latent.space/p/llm-training-2024), [cluster-health repo](https://github.com/imbue-ai/cluster-health), [Imbue infra post](https://imbue.com/research/70b-infrastructure/)); SemiAnalysis's ClusterMAX rates GPU clouds and names storage as a hidden cluster cost — "a slow storage system can make job initialization take longer, checkpointing slower, and recovery more painful" ([ClusterMAX](https://clustermax.semianalysis.com), [SemiAnalysis video](https://www.youtube.com/watch?v=whvik_QgN30)).

## 5. The five storage behaviors a training tenant would demand certification for

Distilled from everything above — these are the behaviors that actually decide whether a cluster is trainable, each with the public precedent that defines it:

1. **Synchronized burst checkpoint writes at fabric scale, with a bounded training pause.** Certify that N×thousands of ranks writing 1 MB–4 GB each (0.78–7.5 TB total per checkpoint) complete inside the tenant's pause budget: aggregate sustained ≥2 TB/s and peak ≥7 TB/s class for a 16k-GPU fabric (Meta's Llama 3 numbers), ≥10 GiB/s per node on the batch-write path (DeepSeek), write tier ≥½ of read tier (NVIDIA RA), thousands of ranks committing in hundreds of milliseconds staged / seconds durable (Meta, DeepSeek) — and that egress spikes, congestion, timeouts, and retries never stall GPUs during the burst (Meta's concurrency-control lesson). Sources: [Llama 3 §3.3.1](https://arxiv.org/html/2407.21783v3), [Fire-Flyer §VII-A](https://arxiv.org/html/2408.14158), [DGX SuperPOD RA](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-b200/latest/storage-architecture.html), [Meta blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/), [nvCOMP](https://developer.nvidia.com/blog/cut-checkpoint-costs-with-about-30-lines-of-python-and-nvidia-nvcomp/).
2. **Symmetric checkpoint read-back (restore) at the same rates, exercised under failure drills.** The read path is as load-bearing as the write path: reload full weights + optimizer states in seconds-per-node (DeepSeek batch read) to minutes-per-job, measured as part of cluster validation and checkpoint-restore drills (Meta), with the failure drill proving the tenant doesn't lose more than one checkpoint interval of work (DeepSeek: ≤5 minutes; SemiAnalysis: 100-iteration intervals can cost 229 GPU-days at 100k scale). Sources: [Fire-Flyer §VII-A](https://arxiv.org/html/2408.14158), [Meta reliability](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/), [SemiAnalysis](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network), [DGX SuperPOD RA ("do not ignore I/O operations for checkpoints")](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html).
3. **Read-dominant, latency-bounded dataset streaming with no stragglers and no hot spots.** Certify sustained epoch-scale re-reads at the per-GPU rate the model class needs (NVIDIA: up to 4 GBps/GPU for >30 TB vision sets; ~½ that for LLM text), bounded pMax latency so no single slow fetch stalls a synchronized step (Meta), ≥80% of reads served from the L1/L2/L3 cache tiers with ms-level metadata (Meta), random access at scale without prefetch/shuffle gymnastics (DeepSeek 3FS), and no interference with training collectives on shared fabrics (DeepSeek SL/VL; SemiAnalysis straggler analysis). Sources: [DGX SuperPOD RA](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/storage-architecture.html), [Meta blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/), [3FS GitHub](https://github.com/deepseek-ai/3fs), [Fire-Flyer §VI](https://arxiv.org/html/2408.14158), [SemiAnalysis](https://newsletter.semianalysis.com/p/100000-h100-clusters-power-network).
4. **Metadata and concurrency scale: O(1) lookups, synchronized thousands-of-clients events, no metadata hot shards.** Certify metadata resolution in single-digit milliseconds (Meta read-plan cache: 1–2 ms; legacy stacks' hundreds-of-ms lookups were "showstoppers"), no hot-shard amplification when model weights are read concurrently or when GPU-restart storms hit (Meta), and file create/delete + open/close bursts through checkpoint events and dataloader startup without serializing on any metadata server (Meta's "thousands of GPUs… in a synchronized fashion"; Llama 3's per-rank checkpoint files). Sources: [Meta blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/), [Meta GenAI infra](https://engineering.fb.com/2024/03/12/data-center-engineering/building-metas-genai-infrastructure/), [Llama 3 §3.3.1](https://arxiv.org/html/2407.21783v3).
5. **Durability, atomicity, and failure transparency — no silent or torn checkpoints, and attribution when something rots.** Certify end-to-end integrity (checksummed, strongly consistent writes — 3FS/CRAQ; erasure-coded Tectonic), atomic manifest commit so a crash mid-write can never destroy the last good checkpoint (non-atomic checkpointing is documented to consume 12–43% of training time), torn-checkpoint and bit-rot detection on the restore path, per-client telemetry so a stall can be attributed to a specific storage node (Meta's laggards/hedged-reads; DeepSeek's validator), and a scheduled storage-bandwidth stress test on every node before it re-enters the fleet (DeepSeek's weekly validator). The OPT/SDC lessons set the stakes: restarts from untrusted checkpoints "eventually fail." Sources: [3FS GitHub](https://github.com/deepseek-ai/3fs), [Fire-Flyer §VII](https://arxiv.org/html/2408.14158), [Meta blueprint](https://engineering.fb.com/2026/07/01/data-infrastructure/metas-ai-storage-blueprint-at-scale/), [Meta reliability](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable/), [arXiv 2603.03736](https://arxiv.org/pdf/2603.03736), [OPT paper](https://arxiv.org/pdf/2205.01068).
