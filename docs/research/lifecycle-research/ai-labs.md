# AI-lab lifecycle practices: readiness, reproducibility, interruption, and resume

Research date: 2026-10-11. All claims below carry a source URL.

This file marks claims as **[observed]**, **[calculated]**, or **[inference]**. Observed means a source states or demonstrates it. Calculated means arithmetic from source values. Inference means our implication or a proposed rack-bench check. This brief names only model-training labs/trainers as sources. It uses no vendor cloud policy or NVIDIA documentation as substitute evidence.

## 1. Named-lab readiness

### 1.1 OpenAI: gate nodes before scheduling
- **[observed]** OpenAI describes a boot-time “preflight” for its Kubernetes GPU nodes. New nodes receive a taint/label that prevents normal workloads. Test pods run via a DaemonSet. Successful tests remove the gate, so the node becomes schedulable. Its post says active GPU tests take exclusive GPU use for seconds or minutes. They are not suitable as passive background checks.

  [OpenAI, *Scaling Kubernetes to 7,500 nodes*](https://openai.com/index/scaling-kubernetes-to-7500-nodes) (published 2021; source describes its then-current Kubernetes fleet, not NVL72/GB300).
- **[observed]** The same OpenAI post separates always-on passive checks from active boot-time and periodic GPU tests. Passive checks cover reachability, disks, and GPU errors. On detected passive-health failure, the system cordons the node; more serious failures can trigger pod eviction. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
- **[inference]** For rack-bench, use an explicit quarantine → test → release state transition.
  Do not accept “node registered” or “GPU enumerated” alone as readiness evidence. This adapts OpenAI’s taint/label gate, not an OpenAI threshold or rack-specific requirement. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes)

### 1.2 Readiness must include a real distributed launch
- **[observed]** OpenAI reports its large MPI training jobs use one communicator across participating pods. If a pod dies, the job halts and must restart from a checkpoint. It calls pods “semi-stateful,” not freely replaceable. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
- **[observed]** EleutherAI GPT-NeoX documents multi-node launch via Slurm, MPI, or `pdsh`. Users provide a hostfile listing node addresses and GPU slots. Slurm hostfile generation is scheduler-derived. It also notes launcher-specific setup and environment/configuration variations. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox) (live `main`; mutable, examined 2026-10-11; implementation spans historical hardware and software, not a GB300 qualification).
- **[inference]** A quick readiness probe can allocate the intended scheduler path and verify expected ranks. It can execute a tiny collective and bounded training step. It should fail on rank loss or non-finite loss. This adapts GPT-NeoX multi-node launch and OpenAI communicator sensitivity; neither publishes these rack-bench acceptance criteria. [GPT-NeoX](https://github.com/EleutherAI/gpt-neox); [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes)

### 1.3 Named-source operational failures
- **[observed]** OpenAI recounts concrete monitoring failure. Its account traces Prometheus OOMs to an unbounded `/api/v1/series` query from Grafana.
  WAL replay in that account still takes hours after the fix.
  The `GOMAXPROCS=24` setting improves replay in that account. It also describes API-server overload from bursts of node joins and N² endpoint-watch traffic. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
- **[observed]** MosaicML's account shows time spent debugging network filesystems and deleting provisioned cloud storage devices.
  The account also shows time spent waiting for dataset downloads, paying duplicated egress, and fixing incorrect distributed data partitioning. It describes duplicated samples and device-count-dependent data ordering as silent correctness risks. [MosaicML, *StreamingDataset*](https://www.mosaicml.com/blog/mosaicml-streamingdataset) (original MosaicML engineering post; now hosted on Databricks, published 2022; examples use A100-era workloads).
- **[inference]** The lesson for a two-hour check is to validate the training control path and observability too. Cover startup/registration, rank map, telemetry visibility, and one useful step. These short probes catch deterministic faults, not long-tail service reliability. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [Meta OPT report](https://arxiv.org/abs/2205.01068)

### 1.4 Meta OPT-175B: failure diagnosis, node quarantine, and restart
- **[observed]** Meta’s OPT-175B report gives at least 35 manual restarts from hardware failures across two months.
  It also shows failure cycles across over 100 hosts.
  Manual restarts in that account pause training, run diagnostics, cordon flagged nodes, then resume from the last saved checkpoint.
  Meta reports an estimate of 70+ automatic hardware-failure restarts. [Meta, OPT technical report](https://arxiv.org/abs/2205.01068) (v4, 2022; A100-era; counts are Meta-reported estimates).
- **[observed]** The report describes loss divergence recovery. It recommends a lower learning rate and restart from an earlier checkpoint. Loss-scale and activation-norm signals guide restart-point selection. [Meta OPT report](https://arxiv.org/abs/2205.01068).
- **[inference]** Rack-bench can verify node exclusion and restart wiring with a disposable job. It cannot reproduce Meta’s production-scale failure rate or establish convergence behavior. [Meta OPT report](https://arxiv.org/abs/2205.01068)

## 2. Cold and warm bring-up

- **[observed]** MosaicML reports StreamingDataset starting Stable Diffusion on LAION-400m in two minutes on 128 A100s. It fetches batches asynchronously, so training can begin once a batch is available. This is a lab-reported example, not an independent rack-bench measurement or universal startup bound. [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[observed]** OpenAI's boot preflight is an explicit cold-node gate; the post does not publish a cold-versus-warm timing distribution. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
- **[inference]** Distinguish cold and warm bring-up and measure allocation, setup, imports, GPU initialization, rendezvous, useful step, and restore separately. This adapts OpenAI boot preflight and MosaicML streaming startup; neither defines this timing protocol. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [MosaicML](https://www.mosaicml.com/blog/mosaicml-streamingdataset)
- **[inference]** Use isolated job caches for cold tests and preserve shared caches. Report cold coverage as untested where the test cannot establish cache state. This adapts OpenAI’s isolated preflight and MosaicML’s caching discussion, not a published policy. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [MosaicML](https://www.mosaicml.com/blog/mosaicml-streamingdataset)
- **[observed]** MosaicML's StreamingDataset post claims the dataset can begin useful training after a batch is available. Training does not need to wait for a full data download. The post also describes disjoint data subsets across machines. [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[inference]** Keep any data preparation/loading check bounded and synthetic or pre-staged. This category is lifecycle readiness, not a re-test of internet or storage throughput. [MosaicML](https://www.mosaicml.com/blog/mosaicml-streamingdataset)

## 3. Environment reproducibility (including EleutherAI)

### 3.1 What named trainers actually pin or expose
- **[observed]** GPT-NeoX README gives a tested historical range (Python 3.8–3.10, PyTorch 1.8–2.0). It says other combinations may work. It recommends environment isolation because its DeepSpeed fork can break other repositories. It warns that Transformer Engine functionality is not guaranteed with versions differing from its requirements file. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox).
- **[observed]** GPT-NeoX publishes containerized Docker and Apptainer paths, requirements files, configuration examples, and multi-node launch settings. The README states compatible GPU drivers/container tooling are prerequisites and supplies `nvidia-smi` as a sample container workload. This is practical setup guidance, not a claim that a mutable container tag is reproducible. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox).
- **[observed]** GPT-NeoX documents seeds for Python, NumPy, PyTorch and CUDA in its configuration argument reference. Training configuration is YAML passed to its launcher. [GPT-NeoX arguments](https://github.com/EleutherAI/gpt-neox/blob/main/configs/neox_arguments.md); [repository README](https://github.com/EleutherAI/gpt-neox).
- **[inference]** For certification, capture immutable image digest, source commit, requirements/lock hash, and resolved package versions. Capture Python/PyTorch/CUDA runtime, driver and accelerator inventory, launcher/config, and relevant environment variables. Capture seed and model/data revision IDs. A requirements file or seed alone is not full environment identity. [EleutherAI GPT-NeoX](https://github.com/EleutherAI/gpt-neox); [Hugging Face Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint)

### 3.2 Environment drift as a measured failure mode
- **[observed]** OpenAI describes a “preflight” boot gate but does not prescribe package lockfiles or immutable image digests in that post. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
- **[inference]** Do not attribute modern image-digest/lockfile policy to these labs unless explicitly documented. Rack-bench can test reproducibility by recording the actual resolved environment and comparing cold launch, warm launch, and resume manifests. Deliberately alter one harmless version/config field in a disposable run. This verifies drift is visible. [EleutherAI GPT-NeoX](https://github.com/EleutherAI/gpt-neox)
- **[observed]** GPT-NeoX explicitly notes its training checkpoints are not directly compatible with other frameworks. It provides conversion utilities. It distinguishes slim weights without optimizer state from full weights including optimizer states. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox).
- **[inference]** A weight export that loads for inference is not evidence that the training environment or state can resume. Keep training-state artifacts and portable inference weights distinct in both naming and validation. [EleutherAI GPT-NeoX](https://github.com/EleutherAI/gpt-neox)

### 3.3 Version/history caveat
- **[observed]** GPT-NeoX README shows its dependency history before March 9, 2023. The earlier setup uses EleutherAI DeeperSpeed based on DeepSpeed 0.3.15. The v2 migration uses upstream DeepSpeed. The README also recommends environment isolation because the codebase relies on a DeeperSpeed fork. These statements concern repository history/versioned branches, not one coherent current deployed dependency pin. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox).
- **[inference]** Treat README Python/PyTorch ranges as historical tested guidance with version ambiguity. They are not proof of current deployment pins. Capture actual resolved dependencies. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox)

## 4. Spot/interruption/resume

### 4.1 MosaicML/Databricks practice and the numeric spot-fraction gap
- **[observed]** Composer documentation says users can recover from hardware failures, spot-instance termination, loss spikes, or other errors with checkpoints. `autoresume=True` searches for the latest checkpoint using `save_folder` and `run_name`. Rerunning the same code can resume. This includes cases where a system such as Kubernetes resubmits a failed job. [MosaicML Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html) (current stable docs as fetched 2026-10-11; current docs may evolve).
- **[observed]** Composer describes resume lookup order: local `latest-rank{rank}`, then logger/object-store paths such as `{run_name}/checkpoints/latest-rank{rank}`, then `load_path`. Its fine-tuning example explicitly sets `load_weights_only=True` for initial pretrained weights while subsequent restarts use the latest saved run checkpoint. [Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html).
- **[observed]** MosaicML's StreamingDataset post demonstrates GPT training checkpointed every 100 batches. It resumes at batch 100 on 32 GPUs, then at batch 200 on 128 GPUs. MosaicML reports the loss curves match “within numerics.” This is a published lab demonstration, not independent validation for arbitrary workloads or topologies. [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[observed]** MosaicML's Stable Diffusion post describes a 128-A100 primary training run. It says Node Doctor/Watchdog detects failed nodes and resumes jobs. It reports mid-epoch resumption and separate evaluation clusters. [MosaicML, *Training Stable Diffusion from Scratch for $50k (Part 2)*](https://www.mosaicml.com/blog/training-stable-diffusion-from-scratch-part-2) (historical MosaicML platform account; claims are vendor/lab-reported, not independent measured facts).
- **[inference]** This pass finds no verified primary MosaicML/Databricks source for the numeric spot-use fraction. The reviewed sources give no numeric fraction of MosaicML training jobs, GPU-hours, or workload time executed on Spot. **The numeric spot-use fraction remains unresolved.** Composer describes spot termination as a failure scenario, not prevalence. [Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[inference]** Do not turn “up to X% savings” into “X% of training runs use Spot.” Those have different units and denominators. This brief asserts no numerical MosaicML spot share here. [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html)

### 4.2 Meta Llama 3: interruption and recovery evidence
- **[observed]** Meta’s engineering account reports hardware failures in SRAM, HBM, processing grids and network switches. Meta's account shows a material effect on Llama 3 herd reliability. The account describes narrowing NaN propagation via mini-training on progressively smaller clusters. It also describes resuming a reconstituted cluster from a saved checkpoint. [Meta Engineering, *How Meta keeps its AI hardware reliable*](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable) (2025 operational account; not GB300 qualification).
- **[inference]** This supports checking fault isolation and checkpoint continuation, not transferring a failure-rate prediction to this rack. [Meta Engineering](https://engineering.fb.com/2025/07/22/data-infrastructure/how-meta-keeps-its-ai-hardware-reliable)

### 4.3 DeepSeek-V3: infrastructure and bounded recovery evidence
- **[observed]** DeepSeek-V3 describes 2,048 H800 GPUs, eight GPUs per node, NVLink/NVSwitch in-node, and InfiniBand cross-node. In that report, HAI-LLM uses pipeline, expert, and ZeRO-1 data parallelism. DeepSeek reports no irrecoverable loss spikes and no rollback during pretraining. [DeepSeek-AI, *DeepSeek-V3 Technical Report*](https://arxiv.org/abs/2412.19437) (v1, 2024; H800; self-reported).
- **[observed]** The report details communication overlap, custom cross-node all-to-all kernels, FP8 stability techniques, and per-step expert-load monitoring. It does not describe a tested interruption/resume runbook or checkpoint fault-injection result. [DeepSeek-V3 report, §3](https://arxiv.org/html/2412.19437v1#S3).
- **[inference]** Its stability statement does not establish absence of infrastructure faults; it reports no irrecoverable spikes/rollbacks. It cannot establish checkpoint recovery correctness. [DeepSeek-V3 report](https://arxiv.org/html/2412.19437v1)

### 4.4 Full-state resume versus weights-only
- **[observed]** Hugging Face Accelerate says continuing a training state requires model, optimizer, RNG generators, and GradScaler state. Users can register custom objects such as schedulers. The objects need `state_dict` and `load_state_dict` methods. For mid-epoch resume it describes skipping already-consumed dataloader batches. [Hugging Face Accelerate checkpointing](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint) (current docs fetched 2026-10-11; versioned API shown by page links).
- **[observed]** Composer distinguishes loading weights only from normal checkpoint resumption. Its example uses pretrained weights as an initialization. It thereafter loads the latest training checkpoint on restart. [Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html).
- **[observed]** GPT-NeoX labels “slim weights” as having no optimizer states and suitable for inference/fine-tuning; “full weights” include optimizer states. [EleutherAI GPT-NeoX README](https://github.com/EleutherAI/gpt-neox).
- **[inference]** Weights-only means the code restores parameter values only. It may not restore optimizer moments, scheduler progression, gradient scaler, RNG state, data sampler/position, or training step. The code initializes or restarts those components. It is often suitable for fine-tuning initialization, not a faithful continuation of interrupted optimization. [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [EleutherAI GPT-NeoX](https://github.com/EleutherAI/gpt-neox)
- **[inference]** Full-state resume means restoring every state component required by the claimed continuity. Components: model, optimizer, scheduler, scaler, global step, RNGs, sampler/data position, and any custom training state. Even this does not guarantee bitwise-identical future values across different kernels, world size, data order, or nondeterministic operations. Rack-bench must check state completeness and equivalence explicitly. [Hugging Face Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint); [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset)

### 4.5 Checkpoint correctness and incomplete generations
- **[observed]** Accelerate expects save/load through the same training script. It supports custom stateful objects and dataloader batch skipping. It does not claim that arbitrary user data-position logic is automatically correct. [Hugging Face Accelerate checkpointing](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint).
- **[observed]** Composer’s autoresume lookup uses per-rank “latest” checkpoint names and remote logger paths. This makes rank-level artifacts relevant to distributed recovery. The docs do not promise atomicity for every user-defined object store or application checkpoint format. [Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html).
- **[inference]** A file’s presence or successful deserialization is not proof of a complete checkpoint. A distributed checkpoint may have missing rank shards, stale metadata, or an interrupted write. Publish a generation only after all expected shards/metadata exist and pass validation.
  Keep the previous known-good generation. Reject an incomplete candidate or use fallback. This is a proposed validation rule, not a claimed MosaicML or HF implementation guarantee. [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [Hugging Face Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint)
- **[inference]** For a meaningful resume pass, restore the intended latest complete checkpoint.
  Verify rank/shard coverage, step counter, optimizer/scheduler state, and data position.
  Run at least one additional optimizer step. The step must show finite loss and no duplicate/skip in the sample/step ledger. Compare against a same-run control under a stated tolerance; do not require universal bitwise equality. [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset); [Hugging Face Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint)

### 4.6 Anthropic coverage
- **[observed]** Anthropic publicly describes rolling back three days of Mythos Preview RL after reward-hacking behavior. The account shows continuation from a checkpoint before the model's learning of that behavior.
  It also shows changes to training environments. The account describes environment review and recertification before reuse. [Anthropic](https://www.anthropic.com/news/improving-alignment-security-efforts) (training-process account, not a GPU provisioning or general checkpoint runbook).
- **[inference]** This informs rollback and environment recertification but does not document optimizer/RNG/data-position semantics. The bounded review does not verify a public Anthropic GPU bring-up or general resume runbook. This is a sourcing gap, not a claim that none exists. [Anthropic](https://www.anthropic.com/news/improving-alignment-security-efforts)

## 5. Safe two-hour checks for rack-bench

**[inference]** These are proposed measured checks, not lab-prescribed universal thresholds. They adapt published preflight and resume mechanisms and require measured job output. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html)

1. **[inference] 0–15 min: preflight gate.** Capture expected versus enumerated accelerators, runtime/driver/image, and source/config manifest. Allocate a disposable job through the normal scheduler. Verify node isolation/readiness state and visible health telemetry. OpenAI's boot-taint preflight supports the gate pattern, but does not specify rack-bench thresholds. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
2. **[inference] 15–35 min: cold launch.** Run bounded imports, GPU initialization, one CUDA operation and report phase timings from a fresh job-local cache. Do not clear shared caches. Report “cold not exercised” where the test cannot prove cache state. [EleutherAI GPT-NeoX setup](https://github.com/EleutherAI/gpt-neox).
3. **[inference] 35–50 min: warm launch and multi-rank rendezvous.** Repeat with recorded warm cache state; verify every expected rank, hostfile/placement identity, and a small collective. GPT-NeoX documents hostfile and Slurm/MPI launch mechanics; OpenAI documents the all-rank failure sensitivity. [GPT-NeoX](https://github.com/EleutherAI/gpt-neox); [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
4. **[inference] 50–75 min: useful-work gate.** Run a tiny deterministic synthetic batch through forward/backward/optimizer step, check finite loss, nonzero step progression and all-rank completion. “Process started” is not first useful GPU-hour evidence. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes).
5. **[inference] 75–90 min: checkpoint/resume.** Save a complete checkpoint at a boundary. Stop only the disposable job, using its supported cancellation or a process-level signal. Resubmit with the same run identity and pinned manifest. Verify next-step continuity and data position. Test weights-only separately and label it as initialization, not full resume.

   [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint).
6. **[inference] 90–100 min: negative control.** In a disposable checkpoint copy, remove/corrupt one shard. Verify rejection or explicit fallback. Perturb harmless manifest metadata and verify drift reporting. This proposed check builds on Composer per-rank checkpoint lookup and Accelerate state requirements; neither mandates it. [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint).
7. **[inference] 100–120 min: cleanup and evidence.** Stop/delete disposable jobs. Confirm no processes or allocations remain. Remove only job-owned temporary artifacts. Revoke/expire temporary credentials.

   Retain approved logs, manifest, checkpoint ID, rank/step/sample counters, timings, results, and untested conditions. This proposed closeout adapts OpenAI isolation/cordon practice and Anthropic boundary verification; neither publishes this exact checklist. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [Anthropic](https://www.anthropic.com/news/improving-alignment-security-efforts).
- **[inference] Safe boundary:** do not evict unrelated tenants, disrupt scheduler/control-plane services, or power-cycle a rack node to simulate interruption. A supported job cancellation/process signal tests the application handler. It does not prove real spot reclaim behavior or hardware failure recovery. [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [Meta OPT report](https://arxiv.org/abs/2205.01068)

## 6. Limits and interpretation

- **[inference]** A two-hour run can reveal deterministic startup, allocation, rendezvous, drift and checkpoint/resume faults. It cannot establish rare interruption frequency or multi-day reliability. This scope limit follows from the contrast between short preflight guidance and Meta/MosaicML multi-day or multi-scale accounts. It is not a lab-published guarantee. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [Meta OPT report](https://arxiv.org/abs/2205.01068); [MosaicML](https://www.mosaicml.com/blog/mosaicml-streamingdataset)
- **[observed]** OpenAI's examples are Kubernetes fleet engineering from a 7,500-node cloud setup. GPT-NeoX documents software and workflows used across multiple clusters and hardware generations. MosaicML demonstrations are largely 2022-era A100 workloads. None is GB300/NVL72-specific. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [GPT-NeoX](https://github.com/EleutherAI/gpt-neox); [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[inference]** Treat these as published operational patterns, not rack certification criteria with guaranteed thresholds. Apply them to Chennai GB300-class 18-tray NVL72 only through actual measured local results; no source here validates that hardware/topology. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [DeepSeek-V3 report](https://arxiv.org/abs/2412.19437)
- **[observed]** MosaicML's published “same loss curve” result is explicitly qualified “within numerics”. It uses a controlled GPT example across 8, 32 and 128 GPUs. [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[inference]** Do not claim full reproducibility from matching loss alone. Same loss can conceal changed sample order, optimizer state, or skipped/repeated work. Record step and data-position continuity as well. [Hugging Face Accelerate](https://huggingface.co/docs/accelerate/en/usage_guides/checkpoint); [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset)

## Gaps

- **[inference]** This brief examines the primary MosaicML/Databricks sources here. It verifies no numeric fraction of training jobs, GPU-hours, or training time on Spot. Numerator, denominator, period, and hardware scope remain unknown; this bounded search does not prove no source exists. [Composer resumption docs](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html); [MosaicML StreamingDataset](https://www.mosaicml.com/blog/mosaicml-streamingdataset).
- **[inference]** The reviewed sources do not establish GB300/NVL72-specific thresholds, deployed image-pinning policy, or a universal checkpoint commit protocol. This is a bounded evidence limit. [OpenAI](https://openai.com/index/scaling-kubernetes-to-7500-nodes); [EleutherAI GPT-NeoX](https://github.com/EleutherAI/gpt-neox); [Composer](https://docs.mosaicml.com/projects/composer/en/stable/notes/resumption.html)
