## 3. Book guidance: techniques and rack-bench checks

The following source guidance is from the cited text. This note proposes the checks as design applications, not book requirements or measured outcomes. All proposed checks are non-destructive and isolated. Mark a check pass only on recorded evidence. [inference] [Rack-bench scope/background](../books.md)

1. **Plan recovery, checklist, roles, cleanup and rollback.** [observed] Ch. 18 says not to begin recovery without a plan. Checklists should specify tasks, skills, tools/commands, sequence, cleanup, and rollback. [Ch. 18 — Recovery Logistics; Recovery Checklists](https://google.github.io/building-secure-and-reliable-systems/raw/ch18.html) [inference] For lifecycle rehearsal, record named owner/approver, target identity, preconditions, stop conditions, expected restore state, and remaining cleanup time. In the 2-hour window, do not start a drill that cannot safely conclude before the final 20-minute cleanup reserve. [Rack-bench background](../books.md)
2. **Quarantine is incident containment, not routine tenant exit.** [observed] Ch. 18 describes quarantine of potentially compromised hosts/network assets. Quarantine uses visible marking and a tracked list to prevent accidental reuse. It warns quarantine is technical debt requiring eventual remediation.

   [Ch. 18 — Isolating Assets (Quarantine)](https://google.github.io/building-secure-and-reliable-systems/raw/ch18.html) [inference] Rack check: for a disposable incident scenario only, verify the test target is excluded from advertised/schedulable capacity. Verify the quarantine state is visible and owned. Do not label planned tenant offboarding as incident quarantine. Tenant reclaim needs its own admission-stop, workload-disposition, credential-revocation and release workflow.
3. **Rebuild to a known-good state and verify artifacts/state.** [observed] Ch. 18 says reinstalling from known-good images/software is typically preferable for compromised systems. Ch. 9 calls for knowing intended state down to bytes. This includes firmware version/configuration and active/inactive state.

   Ch. 18 “Data Sanitization” specifically concerns verifying source code, binaries, images, configurations and application data against known-good sources/checksums. It is recovery integrity/sanitization of the system ecosystem, not a defined physical-media wipe recipe.

   [Ch. 18](https://google.github.io/building-secure-and-reliable-systems/raw/ch18.html) [Ch. 9](https://google.github.io/building-secure-and-reliable-systems/raw/ch09.html) [inference] For permitted synthetic data, record target identity, known-good manifest/checksums, observed state and mismatches. A matching manifest is not proof of forensic media sanitization. Do not change firmware/OS or perform wipe actions in this bench task.
4. **Revoke access explicitly; do not infer revocation from deletion.** [observed] Ch. 9 calls for an explicit revocation mechanism. It discusses central source of truth, propagated revocation state, failure modes and validation. Ch. 18 separately covers credential/secret rotation during incident recovery.

   [Ch. 9 — Explicit Revocation](https://google.github.io/building-secure-and-reliable-systems/raw/ch09.html) [Ch. 18 — Credential and Secret Rotation](https://google.github.io/building-secure-and-reliable-systems/raw/ch18.html) [inference] On disposable tenant identity only, issue a test credential. Revoke it via the authoritative control. Then verify denial and capture timestamp/result. API/namespace deletion alone is not evidence of credential revocation, workload termination, or data sanitization.
5. **Test safely; evaluate and preserve evidence.** [observed] Ch. 16 calls for testing response plans and automated systems. It offers nonintrusive tabletop exercises. It says to measure response stages, retain artifacts and evaluate failed tests.

   [Ch. 16 — Testing Systems and Response Plans; Evaluating Responses](https://google.github.io/building-secure-and-reliable-systems/raw/ch16.html) [inference] For this 2-hour bench, prefer tabletop or isolated disposable service checks. Capture command/API output, target/version, timestamps, operator, expected-vs-observed state, failures and cleanup result. No live/destructive tests, production mutations, firmware/OS changes, or repeated internet/storage performance tests.

Planned tenant exit/reclaim is a separate design application. Do not cite these passages as proof that deleting a tenant logically deletes its data or sanitizes storage media.
