## 2. What ClusterMAX publicly says it measures

### 2.1 Performance phase: device compute, memory and correctness
- **[observed]** SemiAnalysis starts its GPU-performance evaluation with real-world GEMM performance. It tests grouped GEMMs on cuBLASLt (or hipBLASLt) and DeepGEMM. The tests cover supported precisions: BF16, FP16, TF32, FP32, FP8 E4M3, MXFP8 and NVFP4. Model-derived shapes/batches draw from Kimi K2.5, K3 and DeepSeek V3/V4 projections ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** It also runs GEMM, GEMV bandwidth and MAMF (maximum achievable matmul FLOPS) sweeps per GPU and precision, reporting FLOPs. The described GPU-local memory tests include `nvbandwidth` H2D, D2D and D2H. They also include a custom PyTorch tensor-copy test for pinned H2D/D2H and local HBM copies ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** The HPL-MxP workload tests low-precision linear-system solving and numerical correctness. But it combines compute, HBM, MPI broadcasts, NVLink and scale-out networking. It is therefore not a clean single-device correctness score ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** 3.0 says burst GEMMs “very rarely distinguish providers,” but tests them anyway. A cluster is unusable if they fail. The article says to also check GEMM performance during extended burn-in. Clocks can fall under sustained thermal stress ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** These tests can detect gross underperformance, wrong software/precision support, data-path problems, and some correctness errors during tested operations. Public descriptions do not publish universal per-GPU pass thresholds, tolerance bands, or raw score tables. Do not infer an exact acceptance number from the named workloads ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 2.2 Reliability phase: an 8-hour concurrent stress burn-in
- **[observed]** The described 8-hour burn-in simultaneously runs large Tensor Core GEMMs and all-to-all communication. Its monitor tracks temperature, power, clock frequency, FLOPs, network connectivity, latency, bandwidth and kernel-ring-buffer errors ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** The burn-in can reveal faults that manifest under sustained high utilization, heat and power demand. Such faults include hardware XIDs and obvious performance/clock degradation. It is not a per-GPU thermal characterization sweep. The method reports monitored readings during a workload. It does not use controlled temperature ramps, per-device throttle curves, or thermal margin acceptance bands ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** The article says genuine hardware failures are rare in ClusterMAX testing. Allocations are small and short-lived. The article calls one H100 cluster exceptional. That cluster generated many XIDs over five days. The eight-hour workload is a finite burn-in, not a statistical life test ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 2.3 Fault-injection phase: three distinct mechanisms
- **[observed]** ClusterMAX says it first uses DCGM error injection. If this does not work properly, it writes a synthetic NVIDIA XID/SXID message to the kernel log. Finally, it resets the GPU's upstream PCIe bridge, producing a genuine XID 79. ClusterMAX leaves the health agent and drain automation unchanged. It times detection, time in DRAIN, and return-to-service command readiness ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** These tests primarily assess provider monitoring and remediation response, not GPU quality itself. Treat an injected DCGM error or written log line as deliberate simulated evidence. It does not prove that a GPU physically generated that fault. It also does not show detection of defective hardware ([DCGM injection documentation](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-error-injection.html). [3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** DCGM documentation describes injection as simulating error handling behavior in DCGM APIs. It requires `nv-hostengine`, enabled monitoring (policies or health watches), selecting an injection value, and `dcgmi test --inject`. Examples inject PCIe replay counts and ECC counts. These counts then appear to DCGM monitoring ([NVIDIA DCGM error injection](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-error-injection.html)).
- **[inference]** ClusterMAX's public article does not give the exact injected XID identifier. It also does not give the field number/value or command line for its particular XID test. Do not conflate DCGM's documented generic injection capability with proof for a specific XID. The docs do not show such injection on a given driver/DCGM combination ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [DCGM injection docs](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-error-injection.html)).
- **[observed]** A synthetic kernel-log XID checks consumers that parse kernel logs, but is not hardware detection. ClusterMAX notes that providers' health systems vary in whether they read the kernel ring buffer. Some tests may need coordination so that the trigger is available to its testers ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** PCIe upstream bridge reset is the article's “genuine XID 79” mechanism. It is materially different from a fabricated log record or DCGM field injection. It induces a real PCIe/device failure event. It tests a failure path, not an arbitrary exhaustive set of GPU faults ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** This reset is disruptive and privileged: it requires control over PCIe bridge reset/topology. It can remove a GPU or node from service. The article does not publish a safe exact command, privilege setup, or NVL72 tray-level containment procedure. On a rack-scale NVLink domain, treat it as an operator-approved destructive test. Do not treat it as an ordinary tenant command ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 2.4 GPU quality scoring and health outcomes
- **[observed]** ClusterMAX reports GPU performance measurements (FLOPs and bandwidth), burn-in telemetry, and fault-handling outcomes. It describes per-provider pass/fail performance thresholds at a high level. But it publishes no GPU-only weighted score in the 3.0 article. It also publishes no public numerical threshold table or complete criterion-to-score mapping in that article ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** ClusterMAX's GB300 discussion gives an NVL72 policy expectation. Health checks identify an unhealthy node within two minutes. They also prevent new workloads from scheduling on it. Hot-swapping an eight-GPU node is not the model for NVL72. This is a cluster/node service-health criterion, not a measured GPU silicon-quality grade ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** Published ClusterMAX therefore likely shows a combined GPU-quality signal. The signal combines benchmark performance, stress stability, detected errors, telemetry, and provider response. It is not an explicit stand-alone device certification score. A pass can mean that the tested workloads and checks meet their applicable thresholds. It cannot show that no latent defects or future wear exist ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

## 3. Current NVIDIA diagnostic capabilities: useful beyond published ClusterMAX detail

### 3.1 DCGM Diagnostics can materially extend device screening
- **[observed]** NVIDIA documents DCGM Diagnostics as an administrator-oriented readiness/diagnostic tool. Its coverage includes deployment/software configuration, pending retirements, PCIe/NVLink interfaces, framebuffer/memory, and compute engines. It also covers PCIe replays, permissions/drivers/cgroups, power/thermal constraints, and stress/performance checks. NVIDIA explicitly says Diagnostics are not comprehensive hardware diagnostics. They do not repair faults or replace field diagnosis ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[observed]** The documented run levels distinguish fast readiness checks from Level 3/4 administrator diagnostics. `dcgmi diag -r 3` includes five-minute-by-default matrix/compute diagnostic work that checks written/read data and monitors XIDs, temperature violations and uncorrectable memory errors. The docs provide `dcgmi diag -r 3 -p diagnostic.test_duration=300.0` as an explicit duration override ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** `diagnostic.test_duration` bounds that diagnostic plugin's runtime, not the entire `-r 3` suite. Other selected Level 3 plugins and setup/teardown add time. This flag alone cannot promise total wall-clock duration ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[observed]** The DCGM memory plugin writes/reads patterns and reports memory mismatches, ECC DBEs and L1 cache miscompares. The default allocation is a significant part of framebuffer. The docs document `dcgmi diag -r memory -p "memory.is_allowed=True"`. Level 4 memtest includes address, moving-inversion, random, block-move, bit-fade and memory-stress patterns ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[observed]** DCGM Level 3 targeted power and targeted stress tests drive sustained matrix workloads. They fail on inadequate target power/performance, uncorrectable memory errors, and threshold-exceeding SBEs. They also fail on thermal violations, XIDs and configured PCIe replay/clock limits. Examples include `dcgmi diag -r targeted_power -p targeted_power.test_duration=600.0` and `dcgmi diag -r targeted_stress -p targeted_stress.test_duration=120.0` ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** DCGM's built-in checks provide an actionable candidate for a two-hour per-device qualification. SemiAnalysis does not publicly claim it runs every such test. A rack-wide two-hour budget is different: running lengthy diagnostics serially on 72 GPUs is unlikely to fit. Validate safe parallelism, shared power/cooling limits, and operational isolation on the actual rack and version ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html). [ClusterMAX 3.0](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 3.2 DCGM support and exact limits
- **[observed]** Current DCGM docs list B300 SKU 0x20e6 for the NVBandwidth plugin. The docs also list B200. The fetched supported-product list does not list GB300 or GB300 NVL72 by name. This backs B300 GPU applicability for that specific diagnostic only. It does not show blanket plugin support on GB300. It also does not show support for OEM firmware combinations or the integrated rack ([DCGM Diagnostics: NVBandwidth supported products](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** Do not silently treat a B300 support entry as GB300 rack validation. The same GPU silicon family does not show support for NVL72 topology or integrated NVLink switch paths. It also does not show support for GB300 firmware or a given DCGM release. Check deployed `dcgmi --version`, GPU SKU recognition, and results on the precise rack. Make the check mandatory only after that ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[observed]** NVIDIA documents JSON results and `/var/log/nvidia-dcgm/nvvs.log`. It warns diagnostic processes may run as an unprivileged service account. The docs describe a Level-4 pulse-test log-permission issue and a workaround. The workaround requires stopping/restarting `nvidia-dcgm` or changing its service working directory ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** Diagnostic execution therefore needs the host engine/service configured, GPU access and reserved devices. Pulse test may require root/service intervention. Preserve JSON, logs, DCGM/driver versions and per-device identifiers so a PASS stays attributable and reproducible ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).

### 3.3 ECC, remapping, XIDs, clocks and telemetry
- **[observed]** DCGM health checks show categories including GPU recovery reset, PCIe replay rate, XID errors, faulty memory, and volatile DBE. They also show pending page retirements, retired-pages limit, contained/uncontained errors, row-remap failures and Inforom faults ([DCGM feature overview](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/feature-overview.html). [health monitoring](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)).
- **[observed]** DCGM field identifiers include XID, ECC, row-remapper state, current/app clocks, and throttle reasons. They also include power/thermal violation time, GPU and memory temperatures, and memory max operating temperature ([DCGM field identifiers](https://docs.nvidia.com/datacenter/dcgm/latest/reference/field-identifiers.html). [field ID API reference](https://docs.nvidia.com/datacenter/dcgm/latest/dcgm-api/dcgm-api-field-ids.html)).
- **[inference]** These counters and status fields help a measured before/after delta and during-load telemetry record. They do not prove absence of silent numerical errors, defects not surfaced by telemetry, or a wear lifetime. Nonzero historical counters need interpretation against baseline and policy. Do not automatically treat every lifetime count as a new failure ([DCGM field identifiers](https://docs.nvidia.com/datacenter/dcgm/latest/reference/field-identifiers.html)).

## 4. Is ClusterMAX missing the proposed checks?

### 4.1 Checks present, partially present, or not publicly specified
- **[observed]** **Degraded/DOA devices:** performance benchmarking and GEMM/burn-in can show nonfunctional or grossly slow devices. SemiAnalysis describes provider hardware failures and per-GPU measures. The article does not publish an explicit all-72-GPU DOA checklist or a device-replacement/acceptance rule ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** **ECC/XIDs:** the methodology watches errors during stress and tails kernel logs in burn-in. It also describes explicit injection and genuine PCIe-reset/XID79 reliability tests. These show XID log visibility and provider response coverage. The 3.0 burn-in passage does not explicitly say that it samples an ECC counter collector. Log tailing alone does not show ECC statistics collection. Treat ECC/row-remap coverage from that methodology as unverified, not demonstrated ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** **Thermal/power throttling and clocks:** the methodology records temperatures, power and clock frequency during eight-hour simultaneous stress. Clocks may degrade under heat. The article shows no public GPU-by-GPU thermal sweep or explicit throttle-time score/limit ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** **HBM:** GEMV, nvbandwidth, custom HBM copies and HPL-MxP touch bandwidth/data paths. Performance diagnostic workloads include numerical correctness. Public methodology does not say that the tests cover every HBM address. It also does not publish a dedicated HBM defect screen or ECC threshold ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** **NVLink:** HPL-MxP uses NVLink. The article also describes GPU/network stress and separate scale-up fabric loops. The latter can be rack/fabric-wide rather than per-GPU device-health-only. It stays outside this brief except as it bears on each GPU's NVLink path ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** **Driver/firmware mismatch:** the audit checks software/firmware versions and hardware inventory. Individual provider reports cite stale GPU drivers as a failure. The publicly available 3.0 performance methodology does not enumerate a comprehensive per-GPU driver/firmware mismatch matrix ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [public CLI](https://github.com/SemiAnalysisAI/ClusterMAX)).
- **[inference]** **MIG hygiene:** the 3.0 public methodology and criteria text reviewed for this brief describe no MIG-specific GPU-quality test. Public sources do not show that ClusterMAX checks MIG mode, stale instances, or partition isolation. They also do not show checks of reset cleanliness in GPU performance tests. Treat MIG hygiene as publicly unverified, not definitively absent from its internal process ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [criteria index](https://www.clustermax.ai/criteria)).

### 4.2 SDC: benchmark correctness is not a dedicated screening guarantee
- **[observed]** ClusterMAX's HPL-MxP description explicitly includes numerical correctness, and its GEMM workload runs real arithmetic across several precisions. The DCGM diagnostic plugin also checks correctness of matrix and framebuffer operations ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** This means “SDC screening is wholly absent” is too strong: correctness checks exist within workloads. But the article does not describe a dedicated Tensor Core corruption detector or a reference-oracle methodology. It also does not describe repeated per-device deterministic comparisons or a quantified SDC false-negative rate. The degree of coverage remains unverified ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[observed]** CP-Bench is a separate public PyTorch suite. It advertises deterministic model-level comparisons and operator-level output comparisons across GPUs. These include matmul, attention and normalization. It says a known-good reference run/log is necessary because checksums may vary between environments ([CP-Bench repository](https://github.com/facebookincubator/CP-Bench)).
- **[inference]** A TinyMeg2-class or CP-Bench-style detector may complement a timed screen. The older 1.0 methodology mentions TinyMeg2 as a weekly SDC practice of top providers. But it does not prove that SemiAnalysis ran it on each provider. 3.0 use remains unverified ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [CP-Bench](https://github.com/facebookincubator/CP-Bench)).

### 4.3 What the eight-hour test means for a two-hour certification
- **[observed]** ClusterMAX's stated GPU+network burn-in lasts eight hours. It exceeds the rack-bench per-category two-hour budget by four times ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** Do not call an abbreviated two-hour screen equivalent to ClusterMAX burn-in. A two-hour bench can make a bounded pass/fail claim about measured checks. Longer thermal cycles, intermittent faults and aging remain deferred to smoke/burn-in or lifecycle monitoring ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** A practical two-hour candidate is concurrent GPU-local screening across devices. It includes inventory/baseline, persistent counters, fast DCGM deployment/diagnostic checks, bounded memory patterns, per-device GEMM/correctness and HBM bandwidth. It adds concurrent power/thermal stress with clocks/XID/ECC telemetry, and a short per-GPU NVLink health/error check. Exact concurrency and thresholds require validation against rack power and cooling envelopes. No public source gives GB300 NVL72 wall-clock timings for this recipe ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html). [ClusterMAX 3.0](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

## 5. Practical bench-gpu implications for rack-bench

### 5.1 Candidate device-level checks within a two-hour window
- **[inference]** **Inventory and software identity (minutes):** map all 72 GPUs by stable UUID/PCI BDF. Record model, driver, CUDA/DCGM, VBIOS/Inforom and firmware where exposed. Require expected count and consistent version set. The ClusterMAX audit shows the precedent of hardware/software/firmware inventory. But actual measured version values—not vendor claims—must come from the rack ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [public CLI](https://github.com/SemiAnalysisAI/ClusterMAX)).
- **[inference]** **Baseline evidence (minutes):** collect `nvidia-smi -q`/DCGM per GPU. Collect ECC volatile/aggregate counters, pending page retirement/row remap, failed remap, XID history, clocks, power, temperature and throttle reasons. Distinguish pre-existing/lifetime values from increments during bench ([DCGM field IDs](https://docs.nvidia.com/datacenter/dcgm/latest/reference/field-identifiers.html). [DCGM health](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)).
- **[inference]** **Bounded active test (tens of minutes):** use suitable `dcgmi diag` levels/plugins and per-GPU GEMM + memory correctness tests. Run them in controlled concurrency, retaining JSON and logs. DCGM allows selecting individual tests and setting durations. Its diagnostics are not comprehensive hardware certification ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).
- **[inference]** **Load telemetry:** while compute and HBM stress execute, sample temperature, power, SM/memory clocks, throttle reasons, performance and error-counter deltas. Compare each device with expected SKU-specific policy and peer distribution. Do not invent a universal numeric threshold unsupported by the vendor or validated rack baseline ([ClusterMAX 3.0](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard). [DCGM field IDs](https://docs.nvidia.com/datacenter/dcgm/latest/reference/field-identifiers.html)).
- **[inference]** **NVLink-only scope:** observe link state/error counters per GPU. Use a safe GPU-local peer check where supported. Do not turn this category into a scale-out NCCL/network test. Rack topology and NVLink bridge/switch resets are disruptive. Skip with explicit reason if safe per-device isolation is unavailable ([DCGM health monitoring](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html). [ClusterMAX methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).

### 5.2 Do not claim these checks in a quick PASS
- **[inference]** A nonzero SBE count is a trend signal requiring baseline/rate context. An uncorrectable error, failed/pending remap or new XID is a distinct severity class. Emit raw evidence, deltas and policy outcome rather than collapsing all history into a green/red label ([DCGM field IDs](https://docs.nvidia.com/datacenter/dcgm/latest/reference/field-identifiers.html). [DCGM health monitoring](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)).
- **[inference]** DCGM injection can validate monitoring plumbing but cannot pass “GPU hardware healthy”. Synthetic kernel logs validate log consumers. Only real workload/diagnostic observations and physical fault events provide hardware-origin evidence. Record injection type explicitly ([DCGM injection documentation](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-error-injection.html). [ClusterMAX methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** A clean two-hour result is not a lifetime, wear, burn-in equivalence, or silent-corruption-free guarantee. It certifies only the specific measured workload, device set, software stack, metrics and duration ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html). [ClusterMAX methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** On skip: distinguish unsupported tool/SKU, permissions, unsafe rack-level operation, unavailable GPU reservation, and timeout. Keep the check result skipped with reason. Do not treat missing evidence as PASS ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)).

## 7. Bottom line

- **[observed]** ClusterMAX 3.0 actually tests GPU compute (real and grouped GEMMs, precision sweeps) and GPU memory bandwidth/data paths. It also tests mixed numerical correctness. It runs sustained concurrent GPU/network stress with temperature/power/clock/error monitoring. It checks the provider's response to injected and real PCIe/XID failures ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
- **[inference]** Its strongest publicly evidenced GPU-quality coverage is functional performance under workloads. It also covers whether errors become visible and actionable. It is not a comprehensive, public device-level screening specification. DCGM can add bounded ECC, row-remap, memory-pattern, clock/power/thermal and stress checks. Verify actual GB300/NVL72 SKU support and duration on the target system ([DCGM Diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html). [DCGM health](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)).
- **[inference]** Make the rack-bench two-hour `bench gpu` output per-GPU measured evidence. Make it distinguish ordinary measurements from synthetic injection. It can stay useful and defensible. Do not claim equivalence to ClusterMAX's eight-hour burn-in or a life test ([3.0 methodology](https://newsletter.semianalysis.com/p/clustermax-30-the-industry-standard)).
