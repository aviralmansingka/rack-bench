## 3. Relevant coverage and portable bench techniques

[observed] Wiley’s topic list includes CUDA execution and memory models, streams/events/concurrency, and profiling/performance tuning. Companion sample filenames give concrete evidence of floating-point accuracy/performance examples and asynchronous API examples. They do not establish their exact contents or correctness claims. [Wiley/Wrox catalog](https://www.wiley.com/en-us/Professional+CUDA+C+Programming-p-9781118739327) · [chapter 07 samples](https://api.github.com/repos/deeperlearning/professional-cuda-c-programming/contents/examples/chapter07?ref=master) · [chapter 06 samples](https://api.github.com/repos/deeperlearning/professional-cuda-c-programming/contents/examples/chapter06?ref=master)

1. **[inference] Arithmetic correctness check:** adapt the topic of floating-point accuracy into a fixed-input kernel. Keep seed/build/runtime metadata, checked API results, synchronization, and independent reference comparison. Apply bit-exact checks only where the chosen operation/build guarantees exact repeatability; otherwise define justified tolerances. Record operation, precision/type, tested elements, and elapsed time. The repository filename confirms topic exposure, not this proposed certification procedure. [Chapter 07 listing](https://api.github.com/repos/deeperlearning/professional-cuda-c-programming/contents/examples/chapter07?ref=master) · [CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/)
2. **[inference] Separate accuracy from speed:** report correctness results separately from measured arithmetic throughput. Record precision, kernel/configuration, duration, and clock/power context. A performance example does not supply a GB300 acceptance limit. [Chapter 07 listing](https://api.github.com/repos/deeperlearning/professional-cuda-c-programming/contents/examples/chapter07?ref=master) · [CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/)
3. **[inference] Timed memory test with coverage:** exercise a declared working set and data patterns, and check readback. Report bytes, duration, and coverage, and correlate them with ECC and row-remap snapshots/deltas. N07’s full brief notes a limit of DCGM’s documented default fixed 756 MB working set. That working set may not constitute full-HBM bandwidth coverage on GB300. Neither a sample program nor finite test proves all HBM healthy or zero SDC. [N07 full book brief](../books.md) · [DCGM diagnostics](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html) · [nvidia-smi guide](https://docs.nvidia.com/deploy/nvidia-smi/index.html)
4. **[inference] Controlled concurrency:** use streams/events only when the bench intends to test overlap. Make ordering, synchronization, measured interval and concurrent workload explicit. For a single-device health grade, do not add multi-GPU or east-west/collective performance. Keep only the in-scope per-GPU NVLink health query. [Wiley/Wrox catalog](https://www.wiley.com/en-us/Professional+CUDA+C+Programming-p-9781118739327) · [N07 accepted evidence](../nodes/N07.md)
5. **[inference] Sustained run and telemetry:** run the declared per-GPU workload. During the run, sample clocks, power, thermal data, event reasons, and ECC/XID. Also sample per-GPU NVLink status/counter deltas. Compare with an approved SKU profile or publish measurements without an absolute pass threshold. Preserve failures and exact skip reasons. [nvidia-smi guide](https://docs.nvidia.com/deploy/nvidia-smi/index.html) · [N07 accepted evidence](../nodes/N07.md)
